# Конвенции кода

- Комментарии/доки на русском: ключевая логика, инварианты, неочевидные решения; тексты UI английские.
- Линты: `[workspace.lints]` — `unsafe_op_in_unsafe_fn = deny`, clippy `unwrap_used/expect_used/panic = warn` (в CI `-D warnings`); в тестах разрешены через `clippy.toml`. Намеренное нарушение — `#[expect(clippy::..., reason = "...")]`, не `allow`. rustfmt `max_width = 120`.
- Каждый crate: `[lints] workspace = true`, поля пакета через `*.workspace = true`, зависимости через `workspace = true`.
- Новый crate обязан быть классифицирован в `scripts/crate-boundaries.toml` (иначе guardrail = ошибка); правила зависимостей — данные там, не код.
- `unsafe`/FFI — только в отдельных модулях с `// SAFETY:` (пример: `crates/fasticamera-app/src/logging/logcat_sink.rs`). Платформенный код — `#[cfg(target_os = "android")]`, нейтральная логика рядом и тестируется на ПК.
- Граница JNI: все нативные методы регистрируются в `JNI_OnLoad` (`fasticamera-app/src/jni_exports.rs`) через `RegisterNatives`, сигнатуры — макросом `jni::native_method!` (без экспортов `Java_*`). `jni`/`ndk-sys` разрешены только `android-shell` и `fasticamera-app` (guardrail `jni-ndk-only-in-shell`); нейтральные типы шва — в `shell-contract`.
- `NativeBridge` (initialize/runScenario): логика под `jni_boundary::run_guarded` (паника → `PanicReport`), ответы — JSON со статусом в `status` (serde `tag = "status"`, snake_case); сбой JNI → `ThrowRuntimeExAndDefault`. Колбэки оболочки (`ShellBridge`): политика `LogAndCountCallbackFailure` — исключение в Kotlin не бросается, висящее Java-исключение снимается, ошибка → лог + счётчик `native_callback_failures`. Kotlin только маршрутизирует и вызывает API платформы.
- Главный поток Android никогда не ждёт (только `try_send` в очередь), кроме `surfaceDestroyed` (ожидание квитанции ≤ `surface_release_timeout_ms`) и осознанного опроса вибромотора в `onCreate` (2–3 мс). Вызовы платформы (binder) — вне замков; команды Rust → Kotlin идут через поток `fasticamera-platform`.
- Отчёты/итоги — enum с вариантами (absent/failed/panicked и т.д. не сливаются в bool).
- Конфиг нативной части: JSON от Kotlin (`RuntimeConfig`, `deny_unknown_fields`), дефолты в `android/gradle.properties` → BuildConfig; фиксирован на процесс. Фильтр логов обязан иметь уровень по умолчанию.
- Логи: только `tracing` с `target: "fasticamera::<модуль>"`; тег logcat `Fasticamera` — контракт со скриптами. Мимо фильтра (`logging::emit_unfiltered`) — только паника и строка `FASTICAMERA_RESULT`.
- Smoke-сценарий: логика в Rust (`crates/fasticamera-app/src/scenario/`). Мгновенные (hello, panic) отвечают в `runScenario`; наблюдающие (`ObservingScenario`: lifecycle, permission, motion, platform) живут в маршрутизаторе, пишут стадии `FASTICAMERA_STAGE {json}` и итог позже. Ожидания — `CHECKS` в `scripts/smoke_wait.py` + `scripts/smoke_checks.py`; действия на стадии — таблица `SCENARIO_STEPS` в `scripts/smoke_driver.py`. Отладочные сценарии — за фичей `debug-scenarios`. Функциональные тесты сценариев — через настоящую очередь и маршрутизатор на fake-оболочке (`event_router_tests.rs`).
- Python-скрипты: stdlib, dataclass + чистые функции, отдельный `main`, коды выхода константами, конфиг в TOML рядом; тесты unittest end-to-end через subprocess и временные каталоги (фикстуры копируются, в репо не пишем).
- Bash: общие функции и коды выхода — `scripts/lib/common.sh`; `set -euo pipefail`; проверка `bash -n` в CI (shellcheck не установлен).

## GPU (с сессии 03)
- Каждый объект Vulkan — RAII `Owned*` из `gpu-vulkan::live_objects` (счётчик по видам); сырой `destroy_*` у вызывающих запрещён. Порядок уничтожения — порядком полей/владением; при таймауте GPU объекты намеренно утекают (лучше утечка, чем use-after-free), это видно в `live_objects()` и `detach_failures`.
- Пайплайн нельзя уничтожать раньше цели, чьи кадры на него ссылаются (`VUID-vkDestroyPipeline-00765`): `DisplayChain` держит цель и паттерн вместе.
- Ни одного бесконечного ожидания: таймауты насыщаются в `i64::MAX` нс (`frame_ring::timeout_nanos`), не `u64::MAX`; `vkDeviceWaitIdle` — только запасной путь без maintenance1.
- `extern "C"`/`#[link(` в `gpu-vulkan` — только `src/android/hardware_buffer_ffi.rs` (guardrail `[[source_rules]]` в `scripts/crate-boundaries.toml`).
- Validation: `ValidationMode::FULL` (с sync-валидацией через `VK_EXT_layer_settings`) в тестах и debug; любая ошибка = провал. Известные отступления — только списком VUID с причиной (`gpu.known_validation_deviations`, по умолчанию 02387 и 02384, решение 35), точное совпадение `pMessageIdName`.
- GPU-тесты на ПК — на реальном RADV; нет GPU → тест падает с понятным текстом, `FASTICAMERA_SKIP_GPU_TESTS=1` → явный пропуск; `FASTICAMERA_EXPECT_RADV=1` — проверить имя драйвера.
- Шейдеры: GLSL в `crates/gpu-vulkan/shaders/`, `glslc` NDK (`--target-env=vulkan1.3 -Werror -O`, затем `spirv-val`), путь — `FASTICAMERA_GLSLC` → `ANDROID_NDK_HOME` → `~/Android/Sdk/ndk/<fasticamera.ndkVersion>`; compute с `LocalSizeId` требует `maintenance4` (включена).
- GpuContext не пересоздаётся без нужды; instance, работавший с AHardwareBuffer, не уничтожается до конца процесса (бэклог п. 2).

## Камера (с сессии 04)
- Граница движка — `camera-core/src/{backend,command,event,state,status,config}.rs` + `camera-contract`; её держит главный агент. Команды меняют только желаемое состояние; итог каждой — ровно одно `CommandHandled` (`Accepted`/`AlreadyInState`/`Unsupported`/`InvalidState`), отказ отправки — `CommandRejected::{QueueFull, EngineStopped}`.
- Бэкенд живёт только на потоке `fasticamera-camera`; колбэки NDK никогда не блокируют, только шлют `BackendEvent` с поколением; события чужого поколения отбрасываются со счётчиком `stale_backend_events`.
- Восстановление (решение 39): Evicted/InUse → ждать `Available` (движок помнит последнюю доступность); DeviceFailure/ServiceFailure/TooManyCamerasOpen/неожиданное SessionClosed → повтор по `retry_backoff_ms`; PermissionDenied/DisabledByPolicy → только `EnterForeground`. Счётчик подряд идущих попыток обнуляется лишь после `recovery.stable_frames_before_reset` кадров.
- Темп потока — только по `SENSOR_TIMESTAMP` (`SENSOR_FRAME_DURATION` в режиме CamX ложный).
- Вендорские ключи — только через `VendorCapabilities` (поиск по имени + список разрешённых камер `vendor_frame_duration_override_cameras`); наружу — только `FrameRateMechanism`.
- FFI-время жизни: контексты устройства/результатов освобождаются после `ACameraDevice_close` (looper остановлен); контексты состояния сессии и availability намеренно утекают со счётчиком; слушатель AImageReader — за «воротами» `CallbackGate` (иначе `AImageReader_delete` взаимоблокируется с колбэком, `NdkImageReader.cpp close()`).
- Строка `FASTICAMERA_RESULT` ≤ 4000 байт: большие отчёты — сводка + строки стадий `detail_*`, `smoke_wait.py` печатает их как `FASTICAMERA_DETAIL {json}`.

## Лизинг кадров (с сессии 05)
- Буфер камеры возвращается только явно: `release_after_gpu_fence(fence)` или `release_unused()`; выброшенный лизинг — утечка со счётчиком `leaked_leases` (решение 43). Тесты требуют 0.
- Хаб `raw-frame-stream` только решает под замком; возвраты камере (`AImage_deleteAsync` берёт замок reader-а) — после отпускания (`Deferred`). Порядок замков: хаб → `SharedFrame`.
- Метаданные к кадру — только по точному `SENSOR_TIMESTAMP`; нет пары → `FrameCaptureMeta::Missing{причина}`, чужие не подставлять.
- Reader закрытой сессии не удаляется, пока его кадры на руках (`retired_readers`); удаление лениво на потоке камеры, при остановке — ограниченное ожидание, потом утечка со счётчиком.
- Рендер: прежний кадр отпускается fence-ом более позднего сабмита (спецификация `vkQueueSubmit2`: сигнал семафора покрывает все более ранние команды) или по номеру завершённого сабмита; владение `QUEUE_FAMILY_FOREIGN` — забрать один раз при первом чтении, вернуть один раз в сабмите-заменителе; никаких ожиданий GPU на горячем пути.
- `maxImages` — только из `PoolPlan`; любое исчерпание (`MAX_IMAGES_ACQUIRED`) — счётчик и провал smoke.
- Сценарии с экраном камеры ждут `viewfinder_settle_ms` после первого кадра: AE в начале потока даёт почти чёрные кадры.

## ISP-эталон (с сессии 06)
- Стадия `isp-model` — чистая функция `(&Вход, &параметры) → Выход` своего типа стадии; новые изображения стадий строятся только через crate-private `map_into`/`from_stage_output` (публичные `from_samples`/`from_pixels` — для тестов, кропов и readback GPU).
- Подготовка на кадр (DNG-итерации, обращения) — f64 в `IspParams::resolve`; попиксельно — f32 (`PixelMatrix`), как в шейдере. GPU (07) берёт `IspParams` как есть и сверяется с `pipeline::run_reference` постадийно с явным допуском.
- Настройки «вида» (`ToneCurveSettings`, `GamutCompressionSettings`) — serde-конфиг с `deny_unknown_fields`; значения по умолчанию документируют источник.
- Каждый внешний эталон — фикстура в `test-assets/isp-model/` с командой генерации в манифесте; расхождение с эталоном объясняется в тесте (пример — LibRaw берёт только ColorMatrix1).
- Интеграционные тесты: общий `tests/support/` (`load_asset`, `real_capture`); `#![allow(clippy::unwrap_used, clippy::expect_used, reason = ...)]` на бинарь теста.

## Рендер (с сессии 03)
- Маршрутизатор не держит surface: события → `RenderInbox`; квитанция освобождения — только поток рендера ПОСЛЕ detach. Бюджет: `max(acquire, teardown) + teardown ≤ render.release_receipt_budget_ms (450) < shell.surface_release_timeout_ms (500)` — проверяется конфигом.
- Сценарии, которые долго работают с GPU, — на рабочем потоке (`scenario/background_job.rs`) с дедлайном `scenarios.gpu_job_timeout_ms`; маршрутизатор только опрашивает.
- Политика показа по умолчанию (07): `NearestFeasible` + поздний захват кадра камеры + сход на ближнюю линию пропуском одного vsync (решение 54); стоимость кадра = CPU + GPU (измеренное). На телефоне сход не срабатывает: время GPU растянуто DVFS (решение 57, бэклог — выполнимость по фактическим опозданиям). ADPF (`APerformanceHint`) — по умолчанию выключен.
- **Замер на Adreno:** мс GPU (timestamp-запросы) ≠ стоимость работы — DVFS растягивает работу до бюджета кадра (мозаика 05 и весь ISP оба ≈ 12 мс). Мера цены — ток (A/B, мА), мс GPU ловят только грубые ошибки. На ПК (RADV) мс GPU честны.

## Лизинг и видоискатель (с сессии 07)
- Кадр камеры, прочитанный ISP, возвращается fence-ом СВОЕГО сабмита (не следующего); видоискатель — буфер на 1 кадр (`raw_frame_stream::ViewfinderPacing::JitterBuffer`, решение 53): каждый кадр сенсора показывается ровно один раз, одна выдача на показанный тик; сброс — только дрейф часов камеры против экрана (счётчик `jitter_overflow`).
- Параметры ISP — только своего потока (привязаны к `Arc<StreamPassport>`); чужие нейтраль/уровни/матрицы не подставляются, нет параметров — кадр отпускается со счётчиком.

## GPU (с сессии 07)
- Слот кадра: `collect`/`release_slot_after_fence` до перезаписи; пул timestamp-запросов — на слот (общий пул ловит validation при сбросе с CPU); `FrameSink::abort_frame` после ошибки записи команд; `is_backdrop_current` (поколение картинки).
- Варианты SPIR-V `_subgroup` — по возможностям устройства; ожидание fence камеры — на стадии `ALL_COMMANDS` (без maintenance8 иначе нельзя).
- `fma` и деление в Vulkan неточны (деление до 2,5 ULP): где нужна бит-в-бит точность (Menon), деление — `divide_correctly_rounded`, порядок сумм — `precise`.

## 3A (с сессии 08)
- Движок уровневый и для 3A: тап — желаемое `PointOfInterest::Point{region, request = CommandId}`; триггер выдаётся исполнителем, пока движок не подтвердит отправку (`trigger_submitted`), повторный reconcile его не дублирует. Все решения «как выполнить» — в реализациях `ExposureController`/`FocusController`; заменить часть = новая реализация, планировщик не трогать.
- Каждый запрос (повторяющийся, триггер, серия) строится одним путём плана: рычаг частоты и вендорские ключи CamX — в каждом (ключи HAL «липкие», разовый запрос без них может сменить режим сенсора).
- Результаты с `RequestOrigin` ≠ `Repeating` идут невытесняемой полосой ящика и НЕ входят в темп потока (`cadence`) — они обгоняют очередь кадров. `Unknown` — как поток.
- Отказ `Backend` разового запроса (триггер, серия) сессию не ломает — явный итог (`TriggerNotDelivered`, `SubmitFailed`); `DeviceDisconnected`/`NoSession` — восстановление.
- Ручные значения не обрезаются молча: `ControlsAdjusted` + `ThreeAStatus.adjustments` (диапазон камеры, длительность кадра потока, шаг EV). Полуавтомат: у вендорского AE — `Unsupported(SemiAutomaticExposure)`, у нашего (с 08a) — поддержан, упор в предел → `TargetNotReached`.
- Опознание запроса в колбэке NDK — целый ключ в `ACaptureRequest_setUserContext` (0 — нет контекста → `Unknown`, 1 — повторяющийся, ≥2 — разовые из таблицы с ёмкостью; ёмкость ≥ длина серии + 8 проверяет конфиг приложения). Ключ не разыменовывается.
- Пустой 3A-поток (YUV 640×480, без целей в запросах) — только в `camera-android` за конфигом `three_a_companion_stream`; не поднялся → сессия без него и `three_a_companion: unavailable` (smoke `viewfinder`/`3a` валится).
- AWB: нейтраль ISP — только от нашего AWB своего потока (`neutral_for_white` по DNG-профилю потока); подсказки HAL (`COLOR_CORRECTION_GAINS`) — только диагностика; тест «изменение подсказок HAL не меняет `IspParams`». Между модулями ходит точка белого (цветность/CCT+Duv), не нейтраль. Оценка — «в форме шейдера» (f32, таблица на поток, без итераций) за трейтом исполнителя (решение 68). Сглаживание — по меткам сенсора на каждом показанном кадре, статистика прорежена (`statistics_every_n_frames`); холодный старт скрывает кадры не дольше `max_hidden_frames`. Кадры серии (`Burst`) видоискатель не показывает и AWB не берёт (`bracket_frames_skipped`).
- Замер цены стадии AWB — с `statistics_every_n_frames = 1`, иначе прореживание искажает A/B.

## Наш AE (с 08a)
- Рендер — «разведчик» (меряет сцену, предлагает «выдержка×ISO для среднего серого при EV 0»), движок — «тренер» (EV, блокировка, полуавтомат, делёж, мерцание, пределы → `ExposurePlan::Sensor`, `AE_MODE_OFF`). Рендер не знает диапазонов камеры, движок не знает статистики.
- Замер использует «выдержку×ISO» только из результата, спаренного с этим кадром; нет пары — пропуск со счётчиком, никогда не подставлять запрошенное.
- Усреднение (13c, решения 133–134): по умолчанию ОБЫЧНОЕ среднее света (`MeteringConfig.scene_average = LinearLight`; `LogLuminance` — прежнее лог-среднее, только для A/B). Пересвет — нижняя оценка, не растёт с выдержкой: его вклад ограничен `clipped_max_share_of_target` (0,5) от цели С ЗАЩИТОЙ светов и ВЫЧИТАЕТСЯ из цели: `log2 P* = log2 P + log2(T' − c) − log2(m)` (а не `P·T/Y` — иначе замер зависит от выдержки и EV ±1 даёт ×3/×0). Инвариант «одна сцена при P/2, P, 2P → одна P*» закреплён тестом. Фон точки `spot_background_weight` 0,0001 (0,001 при обычном среднем «затягивал» тап ярким окном).
- `3a`: шаг EV сам сбрасывает точку замера (`reset_point_of_interest`, решение 135), точки несут `metered_area`. Старый дефект 08a: полоса `Partial` (≥35 % пересвета) + EV −1 → экспозиция в ноль — в сессии 15.
- `ExposureController::plan` — чистая функция (зовётся и в `validate`); состояние меняют только `refresh`/`observe_result`/`reset_for_new_stream`. Детектора мерцания больше нет (решение 77): защита — ручная политика `flicker = "never_protect"` (умолчание) / `"always_protect"` + частота сети из конфига; `FlickerProtection` — единственный владелец периода кратности, `scene_flicker` HAL — только наблюдение.
- Частота перестроения запроса ограничена дважды: рендер публикует не чаще `publish_min_interval` и при изменении ≥ `publish_min_change_ev` (первое предложение потока — сразу), движок не пересобирает план ниже `replan_min_change_ev`.
- Поправка `ExposureTarget/TargetNotReached` — относительная (`requested = 0`, `applied` = нехватка, округлённая шагом из конфига), иначе `ControlsAdjusted` сыплются на дрожании цели.
- Остаточная подтяжка ISP `k = D/A` (±`max_residual_ev`, квантуется `residual_gain_step_ev`; `UNITY` — старый путь бит-в-бит) — часть `IspParams` кадра; снимок (14) обязан повторять `k` своего кадра. При `camera.exposure_controller = vendor` или без рендера AE `k = 1`.
- Приёмка AE (08c): «ноль вендорского AE» судится по учёту движка `ThreeACounters.results_with_hal_ae_active` с его запуска (каждый результат), а не по выборке сценария; доказательство блокировки — размах сырого замера под ней (`observed_scene_range_ev`), неподвижная сцена — заметка, не провал. Пробел: ПК-стенд AE не проходит путь статистики `subgroupAdd` + RAW10, по которому идёт телефон.
- Тесты AE: замкнутая симуляция с задержкой сенсора 8 кадров и прореживанием статистики (`scene-estimation`), GPU-стенд «камера отвечает на предложения» (`render-loop/tests/vulkan_ae_scene.rs` + `ae_rig`), сквозной `3a` с fake-AE рендера (`fasticamera-app/src/fake_render_ae.rs`).

## UI (с 10)
- `ui-core`: никаких `Instant::now()` — время из меток касаний и vsync (`MonotonicNanos`); физика — от «сейчас − старт», без накопления dt (60 и 120 Гц побитово равны). Таймеры жестов тикают от кадров (`UiInput::Frame`).
- Удаление элементов — только `UiScene::remove_subtree` (снимает жесты и анимации); сцена не отдаёт `&mut UiTree`.
- Один движок прокрутки (`ScrollAxis`) для карусели и всех шкал; одно правило Reduce Motion (`Spring::for_motion`); своей физики в `ui-kit`/экране не писать.
- Числа экрана — только в токенах `ui-kit`/конфигах с меткой происхождения (`[doc]/[measured]/[review]/[reverse]/[derived]/[estimate]`); оценки — «подгонка, не Apple». Элементы `ui-kit` не знают предметной области (токены — дизайн-система экрана, им можно).
- Жест → элемент `ui-kit` только через `PanUpdate::from_gesture` + `apply_pan(event.time, …)`; время — метка касания события, не время кадра.
- Системная отмена (`Cancelled`) = «без действия»: карусель возвращается к выбору до жеста без событий; шкала — отпускание без скорости (значение менялось вживую).
- Ловушки (дока `UiScene`): `layout()` после смены структуры; кнопка = `Tap` + `Press` (один `Press` внутри тапа видоискателя срабатывает вместе с фокусом); пан + свайп на одном элементе — только `pan.require_to_fail(swipe)`.
- Ведение за пальцем: движение от `from_recognition` (без скачка на гистерезис), захват едущего — `freeze_property` на касании (`Press`), отпускание — пружина со скоростью пальца.

## UI-рендер (с 11)
- Формулы рисования — источник истины в `ui-draw` (CPU, «в форме шейдера», f32); шейдеры `ui-render-vulkan` их повторяют, паритет — тестами с явным допуском. Новая формула сначала в эталон, потом в GLSL; копии констант в GLSL держат тесты паритета.
- `Affine2` (ui-draw) — строки, `NodeTransform` (ui-core) — столбцы: перевод только через `scene_bridge::node_placement_px`.
- Стекло — «группа» (одна выборка фона, слияние `smooth_union`, ≤ 16 членов); масштаб нажатия запекает строитель списка (`PressParamsPx::scale_for`), рендер его не добавляет. Появление — `effect` (материализация), не прозрачность.
- Проход UI: только после композитора, только при установленном `UiFrameSource`; отказ UI не роняет показ камеры (счётчики + `last_error`); паника `UiFrameSource::produce_frame` ловится в `UiOverlayState::produce_draw_list` (не общим `catch_unwind` итерации — тот даёт `Faulted`), сломанный источник снимается. Рендер UI создаётся при установке источника между кадрами (`prepare_ui_overlay`), не в первом кадре. Пирамида фона — фрагментными проходами (читатель фона ISP — `Fragment`).
- Свойства стекла проверяются фоном «координатная сетка» (readback = координаты выборки); golden — `FASTICAMERA_UPDATE_GOLDEN=1` (+ `FASTICAMERA_GOLDEN_PREVIEW_DIR` для PNG) — перегенерация только с объяснением, что изменилось в картинке (эталоны зависят от RADV).
- Шрифт/иконки: только символы и иконки из `crates/ui-draw/assets/bake.json`; символ вне набора — `UnsupportedCharacter`, не «тофу». Числа стекла — `GlassStyle` (рантайм-параметры, метки происхождения, «подгонка, не Apple»).
- Время: датчики (гравитация) — BOOTTIME, сглаживание по времени датчика; UI/vsync — MONOTONIC.

## Экран камеры (с 12)
- **Правило решения 96 (с 12a):** элемент интерфейса без эталонного кадра агент не рисует по догадке. Сначала просит кадр у владельца (или ищет запись iOS 27). Если кадра нет, показывает владельцу эскиз того, что придумано, до кода; в коде такие числа — `[estimate]`, «подгонка, не Apple». Источники эталона (решение 102): раскладка и поведение — iOS 27 (видео C, User Guide 27); числа общих для 26/27 элементов — запись владельца R00 (iOS 26, 3 px = 1 pt), метки `[measured: R00 t=…]` / `[measured: C t=…]`. Записи — вне git, `captures/ios-reference/`.
- `camera-screen` — сборка элементов `ui-kit` (решение 84): свою механику/рисование в экран не писать, если их даёт `ui-kit`; общее при втором использовании — в `ui-kit`. Числа виджетов — `widgets_config.rs` с метками происхождения; координаты — iPhone (956 pt) с привязкой к низу, сдвиг считает `ScreenLayout`.
- Один владелец значения: `ScreenState` владеет EV/режимом/панелью/индикатором фокуса (и его сроком — `FocusFrame` в виджете с `FocusHold::UntilReleased`), элементы `ui-kit` — только физикой. Программная синхронизация элемента из состояния не порождает действий (гашение эха). `ExposureRestored` — только синхронизация экрана со значением камеры, камере ничего не шлёт.
- Редьюсер чист: время только из действий (`at`, `Tick`); отказ (`Rejected`) не меняет состояние, кроме продвижения часов и сброса раскладки при `InvalidSurface`. Подтверждение блокировки AE/AF — только вместе с точкой камеры новой блокировки; точки камеры сопоставляются с последним тапом по координатам (номера запроса экран не знает).
- Палец на «солнце» продлевает жизнь индикатора фокуса действием `FocusSunHeld` на каждом событии пана (даже без смены шага EV); «новый показ» рамки (пульсация) — по номеру показа `FocusState::presentation`, а не по времени/координатам. Ответы фейк-снимка привязаны к эпохе экрана (`CaptureCompletionSlot`): после переустановки экрана старые ответы снимаются со счётчиком.
- Порядок рисования экрана: маска/фон вне кадра → сетка/уровень → рамка/плашка → стекло → содержимое; шторка меню (стекло + содержимое) — последней, всё под ней рисуется раньше.
- Карточка инструмента (с 12a, решение 103): `PanelState::Submenu(tool)` и `ExposurePanel` — обе «карточки», происхождение — `CardOrigin` (внутреннее; виджеты спрашивают `card_returns_to_menu()`), левая кнопка = `SubmenuBackRequested` (из меню → меню, со значка → закрыть), выбор варианта карточку НЕ закрывает, свайп вниз закрывает любую панель (нечего закрыть → `NoChange(NothingToClose)`). Затвор: под меню `HiddenUnderDrawer` (не жмётся), при карточке `RaisedAboveCard` (поднят на `card.raised_shutter_offset_pt`, жмётся В ПОДНЯТОМ месте — рамка трекера нажатия следует за смещением). Нижний ряд (миниатюра, капсула, кнопка меню) при карточке гаснет и не принимает касаний (`is_bottom_row_hidden`). Морф карточки переиспользуется только при том же виде (`FromSheet`/`InPlace`). Координаты содержимого карточки — от её центра. Reduce Motion: без перемещений и масштаба, только растворение.
- Экран живёт на потоке рендера; вход — ограниченный канал из роутера, эффекты исполняет приложение там же без ожиданий (`CameraHandle` try_send, хаптика, галерея, `SetFraming`, фейк-снимок). Smoke-сценарии снимают экран, если не объявили `CameraScreenPolicy::KeepRunning`; место видоискателя (`SetFraming`) сценарии не откатывают.
- Клавиши громкости: Kotlin `dispatchKeyEvent` → Rust; потреблять (`true`) только доставленное в очередь событие.
- Датчики экрана (с 12b): гравитация — у источника на потоке рендера (`GravityLink`), ориентация — у установленного экрана (`InstalledScreen::_orientation_sensor`, RAII); обе живут ровно столько, сколько экран, на время сценария отпускаются (датчики «заявленные»: второй подписчик получил бы отказ). Имя пакета для `ASensorManager` — факт процесса из `initialize` (решение 106), не из подключения Activity: на ПК fake-оболочка этого порядка не видит — проверять `dumpsys sensorservice` на телефоне при обычном запуске.
- Тесты, подающие `ShellEvent` напрямую, не доказывают, что событие вообще рождается: для потоков от датчиков проверять и подписку (fake-датчик со счётчиком живых подписок, `orientation_sensor_fake.rs`).
- Системные панели скрыты (решение 95), свайп от края показывает их временно и ПРИХОДИТ в приложение. Касание, палец которого опустился в обязательной зоне системного жеста (`mandatorySystemGestures` через `getInsetsIgnoringVisibility`, `ShellEvent::SystemGestureZones`), экран не обрабатывает до конца этого указателя (`CameraScreen::set_system_gesture_zones`, счётчик `touches_ignored_in_system_gesture_zone`); сервис экрана помнит последние зоны и отдаёт их каждому новому экрану. Скрытие панелей повторяется в `onWindowFocusChanged(true)`.

## Зум и смена камер (с 13)
- Одна шкала зума: `camera-contract::zoom` — `ZoomRatio` (относительно опорной камеры направления: задние — основная), `ZoomCatalog{back, front}` строит ТОЛЬКО `camera-core::zoom::build_zoom_catalog` из характеристик (коэффициент = эквивалент фокусного / эквивалент опорной, `Optics::equivalent_focal_length_mm`; числа в коде не хардкодятся); 2× — `ZoomStopKind::DigitalCrop`, настоящий объектив рядом его вытесняет.
- Кадрирование по зуму — ОДНА формула `ZoomFraming{aspect, facing, ratio, catalog}::crop_for_camera(camera)`: её зовут и экран (тап ↔ сенсор), и рендер — для камеры ТОГО КАДРА, что обрабатывает (`FramingCrop::Zoom`); кадр старой камеры не получает кадрирование новой. Центр кадрирования — оптическая ось (`OpticalAxis` по `intrinsicCalibration`, проверка правдоподобия: заглушки → `Uncalibrated` → центр области); `ViewfinderCrop.center` сдвигается внутрь области, не уменьшается.
- Экран → движок: `LensIntent{facing, ratio, gesture}` через ящик `LensIntentChannel` (последнее побеждает), НЕ через очередь команд. `ZoomGesture::Discrete` (тап по упору, переворот; ОДНО намерение на действие — glide тапа меняет только кадрирование и движку ничего не шлёт) — выбор объектива без гистерезиса и повтор заблокированного после отказа; `Continuous` (колесо, щипок) — гистерезис `switch_up_hysteresis` вверх (только на шаг, без перескока промежуточного объектива), блок соблюдается. Команды и толчок намерения идут по одному счётчику прихода — «позже пришедшее побеждает».
- Машина смены `LensSwitchState{Idle, Steady, Switching{from,to}}` в движке; «объектив показан» (`Idle → Steady`) — с СТАРТА ПОТОКА (`LensSwitchTracker::on_stream_started` из `start_repeating`, 13a: тап до первого результата терял событие), цель, сменённая до старта, — первый показ без события; завершение смены — по ПЕРВОМУ КАДРУ нового потока (`LensSwitched{elapsed}`); перенацеливание A→B→C держит from=A (`LensSwitchRetargeted`). Откат на `from` — только при отказе самой новой камеры (`DeviceFailure`, `ServiceFailure`, `CameraNotPresent`, режим отвергнут после отката частоты); вытеснение/занята/разрешение/политика — обычное восстановление (решение 39). Запрошенный режим (`desired.mode`) не портится: частота камеры = запрошенная или её потолок (`StreamLimitedByCamera`, память на камеру до `Configure`/`Close`).
- Рендер при смене потока держит последний показанный кадр (`continuity.rs`, удержанная картинка ЗАКРЕПЛЯЕТСЯ вынутой из ISP, не копируется) и проявляет новый поток, когда цвет известен и экспозиция правдоподобна (показанный уровень в пределах `max_exposure_error_ev` от ДОСТИЖИМОЙ цели — `exposure/reveal_level.rs`: цель срезана `reach` потока, пределам верим, только если кадр в них лежит; 13a: в темноте сравнение с желаемой целью давало проявление только по сроку), иначе по `max_hold_ms`; кадр пришёл, но непоказуем (`StreamEvent::Unpresentable`) — это активность потока, не «камера пропала». UI узнаёт состояние из `UiFrameRequest.backdrop` (`Live / HeldLastFrame{since} / NoCameraFrame`) и рисует размытие/карточку переворота сам (стекло `GlassRole::Frost`, без новой GPU-машины). Счётчик `black_frames_while_picture_expected` обязан быть 0.
- Выход ISP — картинка фиксированной ёмкости (кадрирование зума 1), содержимое в левом верхнем углу: все читатели (композитор, фон стекла) берут `content_window` / `SourceWindow`, не размер картинки. Зеркало фронта — через окно источника в композиторе И фоне стекла.
- Экран: значение зума — у `ScreenState` (`ZoomState`); первые факты с активной камерой принимаются молча (переустановленный экран не сбрасывает объектив); отказ смены — откат значения без эха намерения; кнопка переворота скрыта, если второго направления нет (инвариант 6); очередь эффектов держит только последний `Lens` и последний `Viewfinder`; щипок — одновременно с распознавателями видоискателя; вибрации колеса — `ui-kit::HapticThrottle` по времени событий (≥ 30 мс).
- Частота камеры (13a): AE `[fps,fps]` выше публичного потолка (16:9 и камеры вне списка CamX) — только если вендорская `SensorModeTable` (`camera-android::sensor_modes`, `CameraRecord.sensor_modes`: `Listed/AbsentOnDevice/Unusable`) даёт родной режим ровно этого размера на этой частоте; иначе `FrameRateNotAchievable` → движок перенастраивает ту же камеру на запасную частоту. Нет таблицы — тоже отказ (фронт на `[60,60]` ронял провайдер HAL). Fake-бэкенд честнее настоящего — сигнал отказа настоящего бэкенда закреплять тестом на настоящих характеристиках.
- Smoke `zoom`: готов к шагам, только когда рендер показал ЖИВОЙ кадр активной камеры (`screen_shows_live_picture_of`; `CameraPresence::Live` = лишь «движок в Streaming»); в записи шага — `continuity` (приращения всех счётчиков непрерывности) и `presented_frames` (метка × камера кадра, первый кадр корзины в мс от действия); `black_frames_before_first_picture` > 0 — провал. Сам приводит экран к «задняя, 1×, колесо закрыто» до шагов и после любого исхода; шаг падает на любом «нечестном» проявлении (`reveal_faults`: проявление по тайм-ауту, честный чёрный «камера недоступна»/«картинки нет», конец удержания без потока) и на событиях смены вне шагов; зазор вибраций в smoke НЕ судится (часы ограничителя — время касаний, а метка вибрации — время кадра UI), только их число; 30 мс доказывают тесты `ui-kit`. Движок помнит намерение, пришедшее до первого `Open`, и применяет его после (`deferred_intent`).
- Приложение: один `LensIntentChannel` в `CameraLinks`; конец сценария возвращает объектив пользователя по роли (`UserLens`), а не роль автостарта; факты `CameraFacts.lens` — `camera_screen_lens_facts` (номер отказа = `switches_failed`).

## Тёплая камера (с 13b)
- Инварианты: кадр тёплой никогда не на экране (хаб возвращает сразу); отказ тёплой не трогает основную (ячейка `Failed`, без повторов до нового спроса); обмен не даёт `StreamInactive`; результаты тёплой не идут в темп/3A/учёт смены/`stale_backend_events` (после обмена — `results_dropped_after_swap`); вне спроса — одна открытая камера.
- Повышение — второй способ того же `Switching`, не вторая машина; отказ обмена → обычное переоткрытие (`promotion_fallbacks`). Режим тёплой ≠ плану → закрыть и переоткрыть, не повышать.
- Никаких «основная/ширик» в логике: ячейки по `StandbySlotId`, ёмкость = min(`standby.max_cameras`, бэкенд), соседи — `zoom::standby_candidates` по каталогу.
- Перенос экспозиции между камерами — ТОЛЬКО `exposure_transfer` (шаг пикселя RAW² / f²), и для тёплой, и для старта новой камеры; рендер узнаёт ожидаемую экспозицию нового потока из `ExposureDirective.stream_start` ДО обмена; предложение AE с другой камеры (`measured_on`) отвергается раньше сравнения по времени (BOOTTIME двух сенсоров перекрываются).
- Гистерезис зума — только на дорогом пути (`SwitchCost::ExpensiveReopen`); с готовой тёплой смена ровно на нативном коэффициенте.
- Оптической оси из HAL верить не всегда: профиль телефона `zoom.untrusted_optical_axis_cameras` (OnePlus 11: `["3"]`, `android/gradle.properties`) → `DistrustedByProfile`, кадр по центру сенсора.
- Снятие спроса — всегда тихим `Continuous` (повтор `Discrete` снимает блокировку объектива); гарантированное «выкл» — `Drop for EffectExecutor` на потоке рендера.
- При повышении ячейка видоискателя НЕ перезаполняется (`PrimingAfterFlush::Keep` в `raw-frame-stream`): перезаполнение повторяло последний кадр старой камеры. Обычная смена потока — `Refill`.
- Рендер помнит объявление `stream_start` ПО КАЖДОЙ камере (`render-loop` `exposure/carried.rs::CarriedExpectations`; `None` = отзыв → забыть все): ящик указаний хранит одно последнее значение, а кадр камеры показывается на 2–3 кадра позже — при частых обменах следующее объявление может перезаписать ожидание раньше первого кадра повышенной камеры (гонка доказана тестом `carried_tests.rs`; что именно она давала удержания на телефоне — НЕ подтверждено). Причина каждого удержания — счётчики `holds_started_*` рендера / `continuity.hold_causes` в записи шага `zoom`.
- Дребезг у отметки с готовой тёплой — каждое пересечение = обмен (решение 130, владелец оставил как есть; «липкий ширик» отклонён).
- Разрыв бесшовной смены судится ЦЕЛЫМИ пропущенными кадрами (`SwitchGap::frames_missed`, порог `max_frames_missed_at_switch` = 2 — решение 132: первые кадры повышенной камеры изредка опаздывают на кадр, разбор в 16a; поле отчёта `frames_missed`), а не дробными периодами: один пропуск на телефоне меряется 2,0003 периода. Метрика — «живой кадр старой → живой кадр новой» (`gap_ms`), `any_frame_gap_ms` — диагностика.

## Снимок (с 14)
- Протокол рендер ↔ запись (`still_contract::develop`): на каждый `StillCommand::Begin`, дошедший до рендера, — РОВНО один итог (`NotSecured` / `PrimaryRendered` / `PrimaryReadback` / `Failed`); `Failed` только после `Secured`. Бэкенд без снимков → поток рендера сам шлёт `NotSecured`; запись итога — метод, забирающий запись по значению, + запасной итог в `Drop`. `PrimaryTargetOffer::Unavailable` → рендер тоже отвечает один `Failed(TargetUnavailable)` (запись считает его опоздавшим). Причины отказа — честные варианты `NoFrameReason` (`RendererBusy`, `FrameUnusable`, `CaptureFailed`, `RendererStopped`), не «нет кадра» для всего.
- Кадр снимка — тот, что был на экране: последний показ с `actual_present ≤ нажатия` (записи драйвера, ждать ≤ `presentation_wait_ms`), иначе `NearestToEstimate` с `PresentationTimingUnknown`. Параметры — запись истории ЭТОГО кадра (белая, `k`), кадрирование — из плана нажатия, охват снимка sRGB независимо от экрана, нейтраль DNG — `neutral_for_white` нашей белой.
- Кольцо: `pick` неразрушающий (`share()`), годный кадр = `Paired` + `RequestOrigin::Repeating`. Пул: `snapshot_capture_holds` учтены в `maxImages` только при кольце > 0; у тёплой эпохи план полный (после обмена её reader — видоискатель), но кадры в кольцо не попадают. Стенды видоискателя/AWB, считающие доли кадров, — с `snapshot_ring_max_frames: 0` явно.
- Копия RAW — один короткий сабмит: приём владения FOREIGN, копия, возврат; лизинг — `release_after_gpu_fence(already_signaled)` после fence копии; у снимка свой импортёр и свои серии. Проявление — не больше `slices_per_frame` полос на показанный кадр и `max_slices_in_flight` в полёте (слоты под копию и показ зарезервированы); `advance_stills` — после `render_and_present`.
- GPU снимков при неизвестном исходе (срок стадии, `WorkStatus::Failed`) — `lose_gpu`: объекты и лизинг — учтённая утечка, следующий снимок пересоздаёт GPU; уничтожать под работающим GPU нельзя. Разбор цели кодера — `try_detach` без ожидания (fence показа maintenance1), без расширения цель откладывается до остановки. Ни одного `wait_idle` на потоке рендера.
- `HostReadbackBuffer::seal(&CompletedWork)` — только доказательством СВОЕЙ работы (`mark_written_by`); `CompletedWork` создаётся только `OneShotSubmitter::poll`. Барьер картинки к копии — `ALL_TRANSFER` (blit ≠ copy в sync2).
- Служба записи (`photo-output::service`): допуск `max_pending_stills` (10) с RAII-билетом, очередь закрывается навсегда под замком (`close_for_good`), паника рабочего потока → итоги всем живым; черновики «всё или ничего» (основной, потом DNG; DNG сорвался после основного → `Saved{raw: None}` + счётчик); сбой Exif → файл без Exif + счётчик; HEIF — Exif `Orientation = 1` (поворот несёт `irot` контейнера, `RotationCarrier`). Сроки экрана — страховка и ДЛИННЕЕ сроков службы (проверка `PhotoConfig::validate` при старте).
- `HeifWriter` 1.2.0: `getInputSurface()` только до `start()`, Exif — с заголовком `Exif\0\0` после `start()`, с `setMaxImages(1)` кончается сам; из своих YUV-буферов — ≈ 6 с и всегда метка «BT.601 полный» (не использовать).
- Smoke: `screen` на время сценария снимает фейком (`KeepRunningWithFakeCapture`); `capture` после проверки удаляет ТОЛЬКО свои файлы (адрес `images/media/N`, владелец = наш пакет, имя `IMG_…`, `DCIM/Camera`), `--keep-captures` оставляет. Служба снимка живёт в `static` (Drop не вызывается) — брошенные черновики убирает уборка при старте.

## Smoke-протокол (с 07a)
- Logcat теряет записи нашего процесса во всплеске записи молча (`__android_log_write` отвечает успехом; счётчик `log_write_failures` такую потерю не видит). Поэтому строка `FASTICAMERA_RESULT` наблюдающих сценариев повторяется (`result_echo`, 5 × 1 с, отмена новым сценарием); стадии не повторяются — критичное не класть только в строку стадии.
- `device-smoke.sh` перед запуском останавливает ВТОРОЙ вариант приложения (`stop_other_variant`, 13a): `am start -S` останавливает только свой пакет, и живой debug своим повтором результата «проводил» прогон release.
- Ожидание logcat в скриптах переживает обрыв беспроводного `adb` (`scripts/smoke_logcat.py`: ждёт устройство, продолжает с метки `-T` без повторов на стыке).
- Сигнал владельцу в smoke-сценариях — подсказка на экране (`OperatorPromptService`), не вибрация (решение владельца, 08c). Подсказка — состояние: висит, пока актуальна; отсчёт идёт ДО момента действия, чтобы не сдвигать окна анализа; снимает её `EventRouter::finish`. Отказ показа (не `Queued`) — провал `ae-trace` / заметка `3a`. Плашка не заходит в центр кадра (`--neutral-card`).
- Подтяжка ISP нашего AE (с 08c): `D = applied.reach.clamp_log2(T + bias)` — `AppliedExposure.reach: ProductReach{Unbounded|Between{darkest,brightest}}` (достижимое запросом при намерении; `three_a_own/plan.rs::reachable_products` через тот же `split` с крайними целями). `applied.shortfall_ev` — только диагностика: он запаздывает на пересборку запроса + 7–8 кадров, и на ступеньке за предел сенсора подтяжка с ним перелетала до 0,5 EV (телефон, `ae-trace`). Яркость экрана в трассе — по показанному кадру (`AutoExposureDiagnostics.displayed_frame_log2_seconds_iso`), а не по последнему результату HAL.
