# Сессия 16: настройки — владелец `app-config` и экраны нашим рендером

Приложи этот файл и скопируй абзац ниже в сообщение.

> Выполни сессию 16 плана `user/foundation/`: создай нейтральный crate `app-config` (владелец настроек: схема с версией, миграции, атомарная запись, битый файл → `.bak` + значения по умолчанию + предупреждение) и настройки нашим рендером (решения 309, 310): быстрые — в камере (шторка Controls PHOTO и выход «Все настройки ›»), полные — отдельным экраном. Экран читает настройки снимком и меняет только намерениями; хранит их один `app-config`. Начни с инвентаризации того, что сейчас настраивается конфигом или параметром запуска. Сначала прочитай `user/foundation/README.md`, `results/02.md`, `results/14.md` и `docs/ios-camera/scope-v1.md`.

## Зачем

**Приоритет владельца (27.11.2026):** «больше есть потребность в хороших и подробных настройках», чем в ручном режиме (решение 307). Сессия — полноценная, а не «страничка Compose»: начинается с **инвентаризации** — агент собирает по коду всё, что сейчас настраивается конфигом или параметром запуска (умолчание, откуда взялось, решение), владелец отмечает «в настройки / скрыть / не нужно». Архитектуру и вид настроек владелец обсуждает до сессии; итоги — решениями в README и правкой этого файла.

Решение 5 ставило настройки на Compose; решение 310 его пересмотрело: настройки рисует наш рендер в языке интерфейса 14p, Kotlin остаётся только для системного. Владелец настроек по-прежнему один — `app-config`: ни экран, ни приложение, ни Kotlin файлы настроек сами не пишут. Решение «битый config → .bak + defaults + предупреждение» перенесено из fastiplayer как проверенная практика.

## Архитектура

- **`app-config`** (Rust, без Android):
  - `Settings` с версией схемы;
  - миграции по шагам;
  - атомарная запись (временный файл + rename);
  - события изменения для подписчиков (`camera-screen`, `CaptureService`).
- **Пункты** — из `scope-v1.md`. Например: формат HEIF/JPEG, RAW по умолчанию, сетка, уровень, зеркальный фронт, «сохранять настройки» (как iOS Preserve Settings: режим, панель, экспозиция).
- **Пресет при запуске** (решение 306): с каким пресетом вида стартует камера — встроенный или свой сохранённый из библиотеки `look-presets`; ничего не зашивается в код, модель основы остаётся внутри пресета (решение 195). Удалённый или испорченный пресет — откат на встроенный с предупреждением, а не отказ запуска.
  - **Полуавтомат: недобор выдержки** (решение 78, 08c): «дотягивать подтяжкой ISP до ±0,5 EV» (по умолчанию) / «как снято». Сейчас поведения «как снято» в коде нет: при исправлении перелёта (`AppliedExposure.reach`) подтяжка всегда тянет к достижимой цели; для «как снято» нужна установившаяся нехватка без запаздывания — спроектировать при реализации.
  - **Качество HEIF** (решение 148, 14c): ручка `photo.service.heif_quality` (сейчас 95 — 13 МБ в темноте, втрое тяжелее JPEG того же качества; аппаратный кодер на 95 бережёт весь шум). Значение по умолчанию выбрать с владельцем по картинке и весу. Шумодава в снимке до плана `video` нет (решения 166, 168), поэтому вес сейчас раздут шумом. Значение выбирается на текущей картинке, а после базового шумодава его пересматривают: тот же уровень качества, вероятно, станет заметно легче.
  - **Защита от мерцания ламп** (решение 77, 08c): «выкл» (по умолчанию) / сеть 50 Гц / сеть 60 Гц → `camera.engine.three_a.exposure.flicker` (`never_protect` / `always_protect`) и частота сети. Автоопределения нет: детектор HAL на этом телефоне фальшивый.
  - **Правило белого при возврате в камеру** (WB36, WB40 плана `white-balance`): «взять у телефона» (умолчание) / «держать последнее». Команда движку `SetWhiteResumeRule` и хранение уже есть (поле `resume_rule` в `white.json`, 16 переносит его в общий конфиг вместе с белой, WB26); параметр запуска `white_resume_rule` после появления тумблера убрать.
  - **Скорость слежения за белым** (WB45, WB56 плана `white-balance`): 0,3 с (умолчание) / 0,1 с и медленнее. Команда движку `SetWhiteFollowSpeed` и хранение уже есть (поле `follow_transition_ms` в `white.json`); параметр запуска `white_follow_ms` после появления переключателя убрать.
  - **Сторона кнопки белого** (WB35) → `camera_screen.screen.white.button_side`.
- **Слои значений:** умолчания в коде → файл настроек владельца (`app-config`) → разовые параметры запуска (только отладка и замеры; после появления пункта в настройках его параметр запуска убирается). Для каждого пункта — «применяется сразу» или «после перезапуска камеры», экран говорит это честно.
- **Шов (набросок, уточнить на старте):**
  - экран (`camera-screen`, нейтральный) шлёт намерение `Effect::Settings(SettingChange)`, приложение отдаёт его `app-config`;
  - `app-config` проверяет, пишет атомарно и публикует `SettingsSnapshot`; экран получает его фактом (как `CameraFacts`), подписчики (`CaptureService`, движок, рендер) — свои срезы;
  - экран держит только снимок для показа, своего хранения нет.
- **Экраны (решение 309):**
  - **быстрые** — шторка Controls PHOTO (уже есть пункты Flash, Aspect, Timer, Exposure, RAW, Grid, Level) + выход «Все настройки ›»;
  - **полные** — отдельный экран нашим рендером: группы, строки, переключатели, выбор из вариантов, подпись-пояснение у пункта; редкое — в «Дополнительно». Камера под полным экраном — пауза или живая: решить по цене и теплу.
  - недостающие кирпичи — в `ui-kit` (строка списка, переключатель, сегменты, заголовок группы); прокрутка `ui-core`, ввод текста — системная клавиатура через Kotlin (как имя пресета в 14b).
- **Эскизы настоящего рендера до кода** (как в 14p): быстрые и полный экран, светлая и тёмная сцена, обе ориентации значков.

## Тесты

- Миграции: файл каждой старой версии → текущая без потери значений. Файл новее нашей версии → не перезаписывается, сессия работает на defaults с предупреждением.
- Битый файл → `.bak` + defaults + событие предупреждения; повторный запуск не множит `.bak`.
- Атомарность: прерывание между записью и rename → остаётся старый корректный файл.
- Сквозной на телефоне: смена формата на JPEG на экране настроек → следующий снимок — JPEG; перезапуск приложения → настройка сохранена.
- Каждый новый кирпич `ui-kit` — тесты по правилам README (отсутствующий ресурс, ошибка, касания и соседство областей, обрезка строк).

## Критерий выхода

- Один владелец настроек, экран без собственной логики хранения. Пункты инвентаризации, выбранные владельцем, работают сквозь до поведения камеры; параметры запуска этих пунктов убраны.
