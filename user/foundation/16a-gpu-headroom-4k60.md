# Сессия 16a: оптимизация GPU под 4K60 с большим запасом (V4)

Приложи этот файл и скопируй абзац ниже в сообщение.

> Выполни сессию 16a плана `user/foundation/`: ускорь полнокадровую цепочку стенда V4 (уровни → качественный демозаик → временной шумодав → вывод в приёмник кадра) на 4096×2304@60 так, чтобы она занимала не больше 25 % бюджета кадра GPU (решение 61). Мерить по методике насыщения ниже, паритет с эталоном `isp-model` держать, тепло подтвердить 30-минутным прогоном. Сначала прочитай `user/foundation/README.md` (решения 50, 51, 56, 59, 61), `results/07.md` (разделы «Стенд V4» и «Таблица стадия → мс GPU → мА») и `results/06.md`.

## Зачем

Решение 61: оптимизация впрок, до финала плана. На видео 4K60 GPU нужен не только под демозаик и шумодав. Главный потребитель освобождённого бюджета — **реалтайм-стабилизатор по гироскопу на compute-шейдерах** (план `video`, п. 3 бэклога README). Это ещё один полнокадровый проход каждый кадр 4K60: перепроекция с коррекцией rolling shutter по строкам. Свободный бюджет нужен ещё кодеру (V5), стеклу UI (11), будущей вычислительной фотографии (план 3) и для того, чтобы телефон не грелся на долгой съёмке (решение 59).

Факт 07a: та же цепочка «в лоб» (f32, 10 отдельных полноэкранных проходов) стоит ≈ 53 мс GPU на кадр при бюджете 16,7 мс. За 10 минут телефон дошёл до теплового статуса critical, а сенсор просел до 36–43 к/с.

**Цель: ≤ 25 % бюджета кадра, то есть ≤ 4,2 мс GPU на кадр 4096×2304** — ускорение примерно в 13 раз. Три четверти GPU остаются свободными.

## Наследство

- 07: `isp-vulkan::quality` — Menon 2007 на GPU (8 проходов, бит-в-бит с эталоном благодаря корректно округлённому делению и `precise`), временной шумодав, `VideoHeadroomWorkload`, приёмник кадра `FrameSink` (V5), сценарий `video-headroom-bench`.
- 07a: мс по проходам на телефоне (таблица в `results/07.md`). Самые дорогие — шумодав 9,3 мс и решение H/V Menon 7,5 мс; остальные проходы Menon 5,5–6,6 мс каждый.
- 06: `isp-model` — эталон Quality-цепочки на CPU (источник истины для паритета).
- Факт 07a про замер: при лёгкой нагрузке Adreno растягивает работу до бюджета кадра (DVFS). Поэтому «мс GPU при показе с vsync» для лёгкой работы — не цена (решение 56).

## Методика замера (договориться в начале сессии, при неоднозначности — вопрос владельцу)

- **Цена = время при насыщении, а не время в темпе vsync.** Режим стенда «без пауз»: кадры цепочки сабмитятся подряд, не по vsync, и меряется пропускная способность (кадров/с при максимальной частоте). Цена кадра = 1 / пропускная способность; timestamp-запросы по проходам снимаются в том же режиме. 25 % бюджета = не меньше 240 кадров/с цепочки на полном кадре. Если без root частоту GPU в насыщение не загнать, это факт для отчёта и стоп-вопрос, а не повод мерить в темпе vsync.
- **Ток**: A/B «стенд вкл. / выкл.» в темпе 60 к/с по методике решения 45 (окна 60 с, ABBA, телефон не на зарядке). До/после оптимизации — в один день.
- **Тепло**: 30 минут стенда в темпе 60 к/с вместе с продуктовым видоискателем и UI на 120 Гц. Кривая по минутам: тепловой статус, запас, температура батареи, ток, к/с сенсора, мс цепочки.
- **ПК (RADV)**: паритет и регрессия скорости по проходам. Там DVFS-растяжки нет, мс честные, но для цели 25 % цифра телефона — решающая.

## Направления (гипотезы — каждая доказывается замером, а не догадкой)

1. **Слить проходы Menon** (8 полноэкранных чтений и записей → 1–2 прохода): тайл в shared memory с «ореолом» (halo) под окно Menon, RAW читается один раз.
2. **fp16** для хранения промежуточных плоскостей и, где паритет позволяет, для арифметики. В 07 для видоискателя fp16 сломал допуск хвоста цепочки — решать замером паритета по каждой стадии отдельно.
3. **Шумодав в том же проходе**, что и вывод; прошлый кадр — в fp16; меньше трафика памяти.
4. **Формат выхода под кодер** (например, 10-бит YUV) вместо f32 RGB, если приёмник кадра (V5) это позволяет без копии.
5. **Под Adreno**: размер рабочей группы, subgroup-операции, раскладка памяти, учёт размеров кэшей. Узкое место (полоса памяти или ALU) — по AGI или Perfetto, если удастся снять без root; иначе экспериментом с откатом.
6. **Место под стабилизатор.** Не закрывать дорогу: выход демозаика и шумодава должен уметь отдать кадр полного поля сенсора (с запасом под кадрирование стабилизации) в форме, удобной для последующей перепроекции, а лучше — с возможностью слить перепроекцию с проходом вывода. Цена такого прохода оценивается здесь же, макетом «поворот + построчный сдвиг» на полном кадре, чтобы проверить, что стабилизатор помещается в освобождённые 75 %.

## Инварианты

- **Паритет с эталоном.** Сейчас Menon на GPU бит-в-бит. Любое ослабление (fp16, приближённое деление, упрощение алгоритма) — **стоп-вопрос владельцу** с цифрами: Δ в LSB выхода, доля пикселей хуже 1 LSB, зонные пластины и края, где Menon выбирает H/V.
- **Продуктовый видоискатель и снимок (14) не ломаются.** Если общий код меняется, нужны их паритет и регрессия на телефоне.
- **Стенд остаётся вне продукта** до плана `video` (решение 51): это задел и цифра, а не фича.
- **Не мешать оптимизацию с рефакторингом границ** (правило 8 `AGENTS.md`): смена API `isp-vulkan` или `gpu-vulkan` — отдельным осознанным шагом.

## Тесты

- Паритет оптимизированной цепочки с `isp-model` Quality: синтетика (зонные пластины, края, цветные полосы, пересветы, около чёрного), реальные кропы RAW10/RAW16, 4 раскладки CFA. Допуск — явный, каждое расхождение объяснено.
- «Старый проход против нового» на одном входе: пока результат обязан совпадать бит-в-бит, это доказательство, что слияние ничего не потеряло.
- Режим «без пауз» на ПК: пропускная способность считается и попадает в отчёт сценария.
- Телефон: `video-headroom-bench` (насыщение + 60 к/с), ток A/B, 30 минут.

## Критерий выхода

- Цепочка 4096×2304 ≤ 4,2 мс GPU на кадр по методике насыщения на телефоне (≥ 240 кадров/с), с таблицей «до/после» по проходам.
- Паритет в согласованном допуске; если он ослаблен — с явным решением владельца.
- 30 минут стенда вместе с видоискателем: без троттлинга (частота сенсора и мс цепочки ровные), тепловой статус не выше `light`.
- Ток стенда A/B до и после.
- Оценка цены перепроекции стабилизатора (макет) по той же методике насыщения: цепочка плюс стабилизатор — с понятным запасом под кодер и UI.
- Если 25 % недостижимы без потери качества — стоп-вопрос владельцу с вариантами и цифрами, а не тихое ослабление цели.
