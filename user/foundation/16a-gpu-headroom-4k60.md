# Сессия 16a: весь GPU приложения — дёшево под Adreno 740 без потери качества (и запас 4K60 для V4)

Приложи этот файл и скопируй абзац ниже в сообщение.

> Выполни сессию 16a плана `user/foundation/`: сделай всю работу GPU приложения дешёвой на Adreno 740 без потери качества. Видоискатель с ISP, модели основы и вид, приборы, стекло и интерфейс, проявление снимка и цепочка стенда V4 — так, чтобы то, от чего телефон сейчас закипает (раздел калибровки: живой видоискатель, прибор на каждом кадре, стекло), стало почти бесплатным по току и теплу. Шейдеры подгоняй жёстко под этот GPU; другие телефоны и GPU не учитывай. Паритет с эталоном держи. Сначала прочитай `user/foundation/README.md` (решения 45, 50, 51, 56, 59, 61, 89, 145, 166–171, 190, 208, 209), `results/07.md` (разделы «Стенд V4» и «Таблица стадия → мс GPU → мА»), `results/06.md`, `results/11.md`, `results/14j.md`, потом этот файл.

## Зачем

**Слово владельца (14j, решение 209):** то, что сейчас закипает, сделать халявой. Удешевить вычисления, не жертвуя качеством, и жёстко подогнать все шейдеры под Adreno 740 этого телефона (пока так). При нынешнем раскладе на телефоне нельзя ни проверять, ни гонять тесты: приёмка 14j остановлена через ≈ 20 минут в разделе калибровки, телефон перегрелся. Исправления 14j (сессия 14k) и остаток 14j ждут эту сессию (решение 208).

Решение 61 остаётся второй целью: оптимизация впрок под видео 4K60. На видео GPU нужен не только под демозаик и шумодав. Главный потребитель освобождённого бюджета — **реалтайм-стабилизатор по гироскопу на compute-шейдерах** (план `video`, п. 3 бэклога README). Это ещё один полнокадровый проход каждый кадр 4K60: перепроекция с коррекцией rolling shutter по строкам. Свободный бюджет нужен ещё кодеру (V5), стеклу UI (11), будущей вычислительной фотографии (план 3) и для того, чтобы телефон не грелся на долгой съёмке (решение 59).

Факт 07a: цепочка V4 «в лоб» (f32, 10 отдельных полноэкранных проходов) стоит ≈ 53 мс GPU на кадр при бюджете 16,7 мс. За 10 минут телефон дошёл до теплового статуса critical, а сенсор просел до 36–43 к/с.

## Две цели

### Цель 1 (главная): продукт на телефоне — «халява»
- **Что считается «закипает сейчас»:** release, раздел калибровки (CALIBRATE) с живым видоискателем 4:3@60, прибором на каждом кадре (решение 190) и стеклом колонки; плюс обычный PHOTO со стеклом. Debug с validation layer — не мера продукта: его нагрев записывается, но не оптимизируется.
- **Что значит «халява» — число ставит владелец по замеру «до»** (в начале сессии, после инвентаризации). Предложение агента для обсуждения, не решение:
  - 30 минут в CALIBRATE с прибором на release, комната, телефон не на зарядке: тепловой статус не выше `light`, частота сенсора и показ ровные, видоискатель без выпавших кадров сверх нынешней нормы;
  - добавка нашего GPU к голой камере (камера без ISP — 358 мА по 07a) — доля, которую назовёт владелец, по току ABBA;
  - прибор, стекло и вид — каждый «не различим» в таблице тока (как стадии ISP после 07a) или с названной ценой.
- **Греет GPU** (слово владельца после 14j, решение 209). Замер «до» нужен не чтобы искать виновника, а чтобы разложить цену GPU по работам (видоискатель, приборы, стекло и UI, вид, основа) и начать с самой дорогой.

### Цель 2: цепочка V4 4K60 — ≤ 25 % бюджета кадра (решение 61)
**≤ 4,2 мс GPU на кадр 4096×2304** по методике насыщения — ускорение примерно в 13 раз. Три четверти GPU остаются свободными.

## Подгонка под Adreno 740 (решение 209)

- **Шейдеры пишутся прямо под Adreno 740 этого телефона** (слово владельца): размеры рабочих групп, плиток и ореола, fp16 по стадиям, раскладка памяти, приёмы тайлового GPU — подбираются под него и живут в самих шейдерах. Про другие телефоны и GPU в этой сессии не думаем: без профилей устройства, без выбора по GPU, без запасных вариантов «на всякий случай».
- **Будущее, не сейчас** (бэклог README): нейтральный контракт GPU-стадий, и под каждый GPU — свой оптимизированный набор шейдеров. 16a его не строит и под него не подстраивается.
- Факты об Adreno 740 и драйвере — сначала проверить на телефоне (`GpuCapabilities`, размер subgroup, поддержка fp16 / int16 / 8-бит хранения, `float32_controls`), потом опираться. Что известно из 07a: мс GPU растягивает DVFS, частоту без root не снять, sysfs закрыт.
- Инструменты профилирования: проверить в начале, что работает без root на этом телефоне (AGI, Snapdragon Profiler, Perfetto с GPU-счётчиками). Не работает — факт для отчёта, тогда замер экспериментом с откатом.
- Направления — гипотезы, каждая доказывается замером:
  1. **Меньше полноэкранных проходов и чтений памяти**: слияние проходов, плитки в shared memory с ореолом, RAW читается один раз (V4 Menon: 8 проходов → 1–2; приборы — накопление в том же проходе, что и видоискатель, или гистограмма в shared memory вместо `atomicAdd` в общую память).
  2. **fp16 для хранения и, где паритет позволяет, для арифметики.** В 07 fp16 сломал допуск хвоста цепочки видоискателя — решать замером паритета по каждой стадии отдельно.
  3. **Не считать то, что не меняется**: прибор, пирамида стекла и вид — только на новом кадре камеры и только при изменении входа; рычаг `every_nth_frame` приборов (решение 190) — по цифрам владельцу.
  4. **Раскладка памяти и проходы рисования под тайловый GPU**: форматы плоскостей, сжатие UBWC, операции загрузки и сохранения вложений проходов UI (не выгружать то, что не нужно), размер промежуточных картинок пирамиды.
  5. **Формат выхода V4 под кодер** (например, 10-бит YUV) вместо f32 RGB, если приёмник кадра (V5) это позволяет без копии.
  6. **Место под стабилизатор.** Выход демозаика и шумодава должен уметь отдать кадр полного поля сенсора (с запасом под кадрирование стабилизации) в форме, удобной для перепроекции, а лучше — с возможностью слить перепроекцию с проходом вывода. Цена оценивается здесь же, макетом «поворот + построчный сдвиг» на полном кадре.

## Шумодав: что здесь не делаем (решения 166–169)

- **Прототип `quality_temporal_denoise` не оптимизировать и не встраивать** в слитые проходы. Он выбрасывается: работает в RGB после демозаика, без компенсации движения, с моделью шума «на глаз». В продукт он не пойдёт.
- В замерах «после» цепочка меряется **без** прототипа (`TemporalDenoiseConfig.enabled = false`). В таблице «до/после» его 9,3 мс стоят отдельной строкой «прототип, справочно».
- **Базовый шумодав** — план `video`, первыми сессиями после модуля движения (решения 166, 171). Он работает на RAW до демозаика, сразу для видоискателя, видео и снимка. Цель качества — без потери деталей и практически без шума.
- **Что 16a ему оставляет:**
  - цифру: сколько из 4,2 мс остаётся шумодаву после ускорения уровней, демозаика и вывода. Если, по оценке агента, остатка не хватит на качество решения 166, это стоп-вопрос владельцу с цифрами до конца сессии. Порога нет: решает владелец;
  - форму: ускоренный демозаик читает мозаику не только из буфера камеры, но и из плоскости очищенного RAW. Шумодав встанет перед демозаиком, и слияние проходов не должно это запрещать (например, вход Menon жёстко прибит к `VkBuffer` камеры).
- Приёмы 16a под Adreno (плитки с ореолом, fp16, раскладка памяти, UBWC) записать в отчёт так, чтобы шумодав плана `video` их переиспользовал.

## Методика замера (договориться в начале сессии, при неоднозначности — вопрос владельцу)

- **Телефон сейчас перегревается за минуты работы — это и есть дефект, который сессия убирает** (решение 145: нагрев — реальная жизнь, не остужать). Порядок прогонов на телефоне планировать заранее: короткие окна, замер «до» в один день с «после», тепловое состояние (статус, запас, температура батареи) пишется рядом с каждой цифрой.
- **Цена = ток и время при насыщении, а не мс в темпе vsync** (решение 56: при лёгкой работе Adreno растягивает время до бюджета кадра).
  - Ток: A/B «работа вкл. / выкл.» по методике решения 45 (окна 60 с, ABBA, телефон не на зарядке). Для продукта: строки «приборы вкл/выкл», «стекло вкл/выкл» (решение 89: `GpuServices::{install,remove}_ui_overlay_for_scenario`, сцена `GlassShowcase`), «вид нейтраль / „Natural“», «основа AgX / legacy», колёса вкл/выкл — в `viewfinder-stage-budget` или рядом, без второго механизма. Сейчас таких строк нет (`results/14j.md`).
  - Насыщение: режим стенда «без пауз» — кадры сабмитятся подряд, меряется пропускная способность; цена кадра = 1 / пропускная способность, timestamp-запросы по проходам — в том же режиме. Для V4: 25 % бюджета = не меньше 240 кадров/с на полном кадре. Если без root частоту GPU в насыщение не загнать — факт для отчёта и стоп-вопрос, а не повод мерить в темпе vsync.
- **Тепло**: 30 минут в CALIBRATE с прибором (цель 1) и 30 минут стенда V4 в темпе 60 к/с вместе с видоискателем и UI на 120 Гц (цель 2). Кривая по минутам: тепловой статус, запас, температура батареи, ток, к/с сенсора, мс цепочки.
- **ПК (RADV)**: паритет и регрессия скорости по проходам. Там DVFS-растяжки нет, мс честные, но решающая цифра — телефон.

## Наследство

- 07: `isp-vulkan::quality` — Menon 2007 на GPU (8 проходов, бит-в-бит с эталоном благодаря корректно округлённому делению и `precise`), временной шумодав, `VideoHeadroomWorkload`, приёмник кадра `FrameSink` (V5), сценарий `video-headroom-bench`.
- 07a: мс по проходам на телефоне (таблица в `results/07.md`). Самые дорогие — прототип шумодава 9,3 мс (здесь не оптимизируется, решение 169) и решение H/V Menon 7,5 мс; остальные проходы Menon 5,5–6,6 мс каждый. Одинаковая цена простых и сложных проходов Menon намекает, что узкое место — полоса памяти, а не арифметика. Это гипотеза, её подтверждает замер.
- 07a: цена ISP видоискателя по току — весь видоискатель +119 ± 11 мА к камере без ISP (358 мА), статистика AWB на каждом кадре была ≈ 55 мА (с 08 — каждый 4-й, «не различим»), остальные стадии ≤ ~15 мА.
- 11a: проход UI (8 стёкол, пирамида фона на каждом кадре камеры) — p95 5,6–6,1 мс GPU на Adreno против ≈ 1,2 мс на RADV; на горячем телефоне `glass`/`screen` валятся по GPU UI p95 8,5–9,7 мс > 8,33 (14c). Цена стекла в мА не снята (решение 89).
- 14h: приборы на каждом новом кадре (решение 190), `atomicAdd` в центр вектороскопа на сером кадре — возможная конкуренция; хост-бенч `isp-vulkan/tests/scope_timing.rs`.
- 14j: ≈ 20 минут в CALIBRATE (debug, validation, parade на каждом кадре) — телефон сильно нагрелся; батарея 43,8 °C после остановки; греет GPU (слово владельца, решение 209); цена по работам не измерена.
- 06: `isp-model` — эталон на CPU (источник истины для паритета).
- **14c (решение 147): подёргивание видоискателя, пока снимки проявляются и пишутся.**
  - Горячий телефон (решение 145): пока идут проявление, кодирование HEIF и запись, джиттер-буфер выбрасывает 4–13 % кадров; без снимков — 1 из 3603 за минуту.
  - Блокировок потока рендера нет (мастерская, решение 144): шаги движка снимков ≈ 1 мс, самый долгий кадр «захват → сабмит» во время снимков < 33 мс. Высота полосы (256 → 32) и `max_slices_in_flight` (4 → 1) долю почти не меняют; выбросы идут всё время проявления и записи, не в моменты работ мастерской.
  - Инструменты 14c: `still.step_cpu` в диагностике снимков, `render_frame_timing` в строке серии `capture`, отладочные логи `fasticamera::raw_stream` («кадр видоискателя выброшен джиттер-буфером») и `fasticamera::render::vulkan` («долгий кадр видоискателя»). Проверить `skipped_ticks_for_depth`/`depth_reductions` за серию (в 14c не сняты), аппаратный кодер HEIC и компоновщик системы.
- **14e (решение 152): блокировка «голова очереди» в мастерской снимка.**
  - Мастерская делает работы по одной. Подключение цели кодера (67–380 мс на горячем телефоне) задерживает буфер копии RAW следующего снимка. Поток рендера выделяет его сам: `still.step_cpu.capture_start` до 62 мс, в логе `fasticamera::render::still` предупреждение «буфер копии RAW из мастерской не успел к снимку: выделение на потоке рендера».
  - Рецепт на выбор: вторая быстрая очередь мастерской для выделений, запас из двух подготовленных буферов, или порядок «буфер раньше цели кодера». Проверка: серия `capture` с лентой `fasticamera::render::still=debug` без единого такого предупреждения и с `capture_start` ≤ единиц мс.
  - Память (факт 14e): Graphics процесса растёт от серии к серии и упирается в ≈ 480 МБ (+185 МБ к покою) после ≈ 4 серий по 5 снимков; при уходе в фон освобождается всё. Если 16a меняет выделения снимка, сверить этот потолок.
- **12b (решение 105): поток рендера пропускает опрос камеры под плотными касаниями.**
  - Трассировка на телефоне: камера отдаёт кадры ровно, а рендер не забирает кадр 25–33 мс.
  - В единственном переполнении, пойманном в окне вместе с фазами, были три итерации подряд по 18–24 мс: сбор слота 6,7 мс, затем `present_with_sync` 13 и 16,5 мс. Линия показа не менялась; переключения 2↔3 случались 57–83 раза за окно при 0–1 переполнении.
  - Запись команд UI под жестами — 2–6 мс на 30–53 элементах.
  - Итог: 0–5 выпавших кадров за 12 с в release, 4–19 в debug. Сценарий `screen` пишет это цифрой `pacing.jitter_overflow` без провала.
  - Здесь: сначала замер на нескольких событиях (чем блокируется `present_with_sync`, что в сборе слота), потом удешевление и возврат порога переполнений в `screen`. Разбивка 12b опирается на одно событие.
  - Временная трассировка 12b откатана. Её патч и логи — вне репозитория, в `~/fasticamera-captures/12b-diag/`, схема — в разделе 12b отчёта `results/12.md`.
- **Из 13b (решение 132), не про GPU, но про темп кадров:** при бесшовной смене объектива первые кадры новой камеры изредка опаздывают на кадр — на стыке пропущено 2 кадра вместо 1 (≈ 50 мс вместо ≈ 33 мс), примерно в 1 смене из 15. Рендер честно перерисовывает старый кадр (`any_frame_gap` — 1 период), то есть опаздывает доставка: камера → поток кадров (`raw-frame-stream`, обмен эпох) → ячейка видоискателя. Разобрать по меткам времени сенсора и прихода кадра; если причина найдена — вернуть допуск smoke `zoom` `max_frames_missed_at_switch` к 1.

## Порядок

1. **Инвентаризация и инструменты** (ПК, read-only разведка + код замеров): список работ GPU выше сверен с кодом; строки A/B для продукта в методике решения 45; поля `scopes` и `float32_controls` в отчёте сценария; режим насыщения для видоискателя и приборов, не только для V4. Код замеров — отдельно от оптимизаций (правило 8 `AGENTS.md`).
2. **Замер «до» на телефоне, release:** таблица «работа → мА → тепло» для продукта (цель 1) и по проходам для V4 (цель 2); факты Adreno 740 (subgroup, fp16, профилировщики).
3. **Стоп-вопрос владельцу с цифрами:** какая работа GPU сколько стоит, порог «халявы» для цели 1, деление сессии (если объём больше одной сессии — например, 16a продукт и 16b стенд V4; решает владелец).
4. **Оптимизации — по убыванию цены из таблицы «до»**, каждая отдельным шагом: замер → правка → паритет на ПК → замер на телефоне → откат, если не помогла.
5. **Замер «после»** в один день с повтором «до» на той же сборке-основе; 30 минут тепла.
6. Хвосты 12b / 13b / 14c / 14e — если остаётся время, после целей 1–2; иначе в отчёт с причиной.
7. Один прогон CI после телефона и фиксов по нему (14g), `results/16a.md`, memories, коммит и push (решение 44).

## Инварианты

- **Качество не теряется** (слово владельца, решение 209). Паритет с эталоном: Menon на GPU сейчас бит-в-бит; паритеты видоискателя, вида и основ — в допусках тестов `isp-vulkan`; приборы — счётчики CPU = GPU бит в бит. Любое ослабление (fp16, приближённое деление, упрощение алгоритма, прореживание приборов, реже пирамида стекла) — **стоп-вопрос владельцу** с цифрами: Δ в LSB выхода, доля пикселей хуже 1 LSB, зонные пластины и края; для UI и приборов — разница на картинке и в задержке.
- **Продуктовый видоискатель, вид, приборы, UI и снимок не ломаются.** Если общий код меняется, нужны их паритет, golden и регрессия на телефоне (`viewfinder`, `glass`, `screen`, `capture`).
- **Стенд остаётся вне продукта** до плана `video` (решение 51): это задел и цифра, а не фича.
- **Не мешать оптимизацию с рефакторингом границ** (правило 8 `AGENTS.md`): смена API `isp-vulkan`, `ui-render-vulkan` или `gpu-vulkan` — отдельным осознанным шагом.

## Тесты

- Паритет каждого ускоренного прохода с эталоном (`isp-model`, `scope-model`, эталон `ui-draw`): синтетика (зонные пластины, края, цветные полосы, пересветы, около чёрного), реальные кропы RAW10/RAW16, 4 раскладки CFA. Допуск — явный, каждое расхождение объяснено.
- «Старый проход против нового» на одном входе: пока результат обязан совпадать бит-в-бит, это доказательство, что слияние ничего не потеряло.
- Golden UI и раздела калибровки — без изменений, если вид не менялся решением владельца.
- Сквозные: видоискатель доходит до показа, прибор рисуется на показанном кадре, снимок проявляется в файл — после оптимизации, а не только по стадиям.
- Режим насыщения на ПК: пропускная способность считается и попадает в отчёт сценария.
- Телефон: строки тока A/B продукта, `video-headroom-bench` (насыщение + 60 к/с), 30 минут каждой цели.

## Критерий выхода

- **Цель 1:** таблица «до/после» по току и теплу для продукта; раздел калибровки с прибором и PHOTO со стеклом укладываются в порог «халявы», названный владельцем, в том числе 30 минут без перегрева. Если порог недостижим без потери качества — стоп-вопрос с вариантами и цифрами, а не тихое ослабление.
- **Цель 2:** цепочка V4 4096×2304 без прототипа шумодава ускорена по методике насыщения, таблица «до/после» по проходам; строка «остаток из 4,2 мс базовому шумодаву» (решение 169); демозаик читает очищенный RAW из плоскости (тест паритета на таком входе); оценка цены перепроекции стабилизатора (макет); 30 минут стенда с видоискателем без троттлинга, тепловой статус не выше `light`. Если цель 2 перенесена владельцем в отдельную сессию — так и записано.
- Паритет в согласованном допуске; если он ослаблен — с явным решением владельца.
- Каждый приём подгонки под Adreno 740 объяснён в отчёте: что сделано, почему это быстрее на этом GPU, цифры «до/после» (вход для будущих наборов шейдеров под другие GPU).
- После 16a телефон выдерживает приёмку 14k / 14j: можно работать в разделе калибровки, не останавливаясь из-за перегрева.
