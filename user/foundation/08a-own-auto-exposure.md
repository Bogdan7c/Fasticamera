# Сессия 08a: наш AE вместо вендорского

Приложи этот файл и скопируй абзац ниже в сообщение.

> Выполни сессию 08a плана `user/foundation/`: замени временный вендорский AE (`VendorExposure` из 08) нашим автоматом экспозиции по статистике RAW — замер по кадру и по точке тапа, плавное схождение без «дыхания», компенсация EV, блокировка, защита от мерцания ламп, делёж между выдержкой и ISO, полуавтомат. Сначала прочитай `user/foundation/README.md` (решения 62–67), `results/08.md` и `results/07.md`.

## Зачем

Решение 63: вендорский AE в продукте не используется, экспозицию ведём сами — главный рычаг ровной экспозиции для видео (V6) и честного полуавтомата в ручном режиме (15). Решение 66: 08 оставила контракт `ExposureController` и временную вендорскую реализацию; 08a доказывает, что часть 3A заменяется новой реализацией трейта без правки соседей.

## Что известно из 08 (зонд `threea`, камера 2, RAW10 4:3@60 CamX + пустой поток)

- При `AE_MODE_OFF` вендорский AF жив (тап → `FOCUSED_LOCKED` ≈ 33 кадра), баланс HAL жив (диагностика).
- Новая экспозиция видна в результате через 7–8 кадров после смены запроса; первый результат с новым тегом уже несёт её. Выдержка квантуется по строке сенсора (8 мс → 7,996 мс, 1 мс → 0,996 мс).
- Паспорт кадра несёт экспозицию и ISO, с которыми снят именно этот кадр, — статистика кадра всегда знает свою экспозицию, задержку конвейера моделировать не нужно.
- Антибандинг HAL: режимы 0–3, по умолчанию AUTO; детектор `android.statistics.sceneFlicker` жив при `AE_MODE_OFF` (видели 0 и 2 = 60 Гц).
- 60 к/с ограничивают выдержку ≤ 16,67 мс; при 50 Гц кратная периоду мерцания выдержка — только 10 мс.

## Архитектура (кратко, уточнить по коду 08)

- **Решение 68: оценка переносима на compute-шейдеры.** Обход плиток, веса замера и редукции — за границей исполнителя оценки на потоке рендера (как у AWB 08): эталон на CPU «в форме шейдера» (f32, таблицы на поток), реализация на compute — сменная. На CPU только скалярное решение для запроса HAL.
- `RawStatsExposure` — реализация `ExposureController` из 08; алгоритм — нейтральный, рядом с AWB (решение 64), на потоке рендера по той же статистике; решение «какая экспозиция» уходит в движок камеры через нейтральный ящик, запрос строит `camera-core`.
- Замер: матричный (веса плиток, защита светов по счётчику пересвеченных ячеек), точечный по региону тапа; цель — средний серый нашего тона (`isp-model`), а не вендорская.
- Плавность: профили `Photo`/`Video` (V6), шаги в EV по времени, без «дыхания»; ограничение частоты перестроения повторяющегося запроса.
- Делёж выдержка/ISO: политика из конфига (сначала выдержка до предела частоты кадров и кратности мерцания, потом ISO); полуавтомат — одна из величин закреплена.
- Мерцание: частота сети из конфига, по умолчанию 50 Гц (решение 67).

## Тесты

- Синтетика: ступенька яркости → схождение за заданное время без перерегулирования; блокировка держит экспозицию при смене сцены; EV ±2 → ×4/×¼ по сигналу; точечный замер по яркому окну не уводит кадр.
- Полуавтомат: `Manual(iso)` + авто → выдержка компенсирует, упор в предел → явный результат «экспозиция не достигнута».
- Телефон: сценарий `3a` расширяется — сходимость к среднему серому на ровной карте, ступенька света (лампа вкл/выкл), отсутствие полос под лампой 50 Гц, A/B тока против вендорского AE.

## Критерий выхода

- Вендорский AE не включается ни в одном запросе продукта (`AE_MODE_OFF` всегда), видоискатель экспонирован не хуже вендорского на эталонных сценах.
- Замена прошла новой реализацией трейта, соседи не правились (кроме композиции).
