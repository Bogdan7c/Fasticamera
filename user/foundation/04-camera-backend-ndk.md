# Сессия 04: камерный бэкенд

Приложи этот файл и скопируй абзац ниже в сообщение.

> Выполни сессию 04 плана `user/foundation/`: наполни `camera-contract`, создай `camera-core` (движок без Android, trait `CameraBackend` и fake) и `camera-android` (реализация на Camera2 — NDK, Java или гибрид по решению из 00): каталог всех камер, включая скрытые, возможности в нейтральных типах, реестр вендорских тегов, жизненный цикл сессии, запросы, ошибки и вытеснение. Кадры здесь ещё не нужны. Сначала прочитай `user/foundation/README.md`, `results/00.md` и `results/02.md`.

## Зачем

Камера — самый капризный ресурс телефона: её отнимают другие приложения, HAL падает на неподдержанных комбинациях потоков, сессии конфигурируются сотни миллисекунд. Если эта сложность протечёт в UI и рендер, каждая фича будет обрабатывать «камера отвалилась» по-своему. Цель — один владелец с явной машиной состояний.

## Наследство 00

- Какие ID видны под нашим именем пакета, открываются ли 4 и 5, как получить телевик.
- NDK, Java или гибрид для управления (если гибрид — Kotlin-часть управления камерой тоже живёт за `camera-android`, наружу не видна).
- Рабочие вендорские ключи и режимы сессии для 60 к/с и для отключения вендорской обработки RAW.

## Архитектура

- **`camera-contract`**:
  - `CameraId`, `LensRole { UltraWide, Wide, Tele, Front }`;
  - `CameraCapabilities`: размеры RAW по форматам и к/с, диапазоны ISO и выдержки, фокус, апертура, DNG-матрицы, black/white level, CFA, тип мозаики, `VendorProcessingFlags` (например, `lens_shading_applied`);
  - `StreamMode` (камера, размер, формат, к/с);
  - намерения `CaptureIntent`, `ManualControl`.
- **`camera-core`**:
  - машина состояний `Closed → Opening → Configuring → Streaming → Reconfiguring → Error(Recoverable | Fatal) → Closed`;
  - команды как intent-методы: `open(role)`, `configure(StreamMode)`, `start_streaming()`, `switch_to(role)`, `apply_controls(…)`;
  - события наружу: `CameraStateChanged`, `CameraUnavailable(Reason)` (вытеснена, отключена, ошибка HAL, нет разрешения — разные варианты);
  - зависит только от `trait CameraBackend`; fake-бэкенд для тестов с программируемыми отказами.
- **`camera-android`**:
  - реализация `CameraBackend`;
  - **реестр вендорских тегов** `VendorCapabilities`: ключи по имени → типизированные setter-ы, проверка наличия при старте; отсутствие → `Unsupported`, а не паника;
  - все объекты Camera2 живут в потоке камеры, колбэки переправляются туда же.
- Логическая камера 5 vs отдельные физические — какой способ давать телевик, решено в 00. Здесь реализуется только он, второй не держим «на всякий случай».

## Что сделать

1. Типы `camera-contract` (без зависимостей), `camera-core` с fake, `camera-android`.
2. FFI (`camera-ndk-sys`, bindgen по заголовкам NDK) или Java-мост — по решению 00. `unsafe` и JNI — только в safety-модулях.
3. Временная поверхность для потока, если HAL не стартует сессию без вывода: YUV-приёмник малого размера, кадры отбрасываются. Отмечено в коде как временное до 05, удаляется в 05.
4. Сценарий `device-smoke.sh camera-catalog`: каталог и характеристики в JSON → сверка с `dumpsys media.camera`.

## Тесты

- Fake: каждый переход машины состояний, включая отказы:
  - вытеснение во время `Configuring`;
  - `ERROR_CAMERA_SERVICE` при `Streaming`;
  - повторное `open` той же камеры — no-op с явным результатом;
  - `switch_to` недоступной роли → `Unsupported`.
- Реестр тегов: отсутствующий тег → `Unsupported`; неверный тип → ошибка; запись не трогает другие ключи запроса.
- Телефон:
  - каталог совпадает с `dumpsys` (ID, роли, размеры RAW);
  - открытие каждой камеры, включая телевик, и получение результата запроса с ожидаемыми ключами;
  - открытие системной камеры поверх нашей → наше событие `CameraUnavailable(Evicted)` и восстановление после возврата.

## Критерий выхода

- Все камеры, доступные по итогам 00, открываются из нашего приложения. Недоступные честно отсутствуют в каталоге.
- `camera-core` тестируется на ПК без телефона, guardrail зелёный.
