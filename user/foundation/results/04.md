## Коротко, простыми словами

1. **У камеры появился один хозяин — движок `camera-core`.** Экран и приложение не трогают Camera2: они говорят движку «хочу камеру такой-то роли, такой режим, поток», а движок сам открывает, настраивает и следит. Состояние камеры всегда видно одним снимком, итог каждой команды — явный ответ («принято», «уже так», «невозможно», «не в том состоянии»), а не «да/нет».
2. **Камеру отняли — движок сам её вернёт** (решение 39). На телефоне: системная камера OnePlus отняла нашу (`cameraserver` записал вытеснение), мы получили событие «вытеснена», а когда наше приложение вернулось на экран, поток восстановился сам за 4,7 с.
3. **60 к/с через NDK — есть.** Основная 16:9 и 4:3, ширик 4:3 — около 59–60 к/с по меткам сенсора, в обоих форматах RAW. Вендорские ключи CamX находятся на телефоне **по имени** и включаются только для основной камеры.
4. **Каталог камер честный.** Роли назначаются по углу обзора: основная 72°, ширик 102°, фронт 71°. Телевика нет, и UI его не покажет.
5. **Найдено и исправлено до телефона** (независимое ревью по исходникам Android): вечное зависание потока камеры при закрытии во время потока кадров, бесконечный цикл восстановления, вечное ожидание «камера свободна», use-after-free контекста колбэка. Подробности — в разделе «Дефекты».
6. **Факт телефона:** логическая камера 0 не отдаёт финальных результатов запросов, только частичные. Кадры при этом идут. Через Java то же самое, то есть это поведение HAL.

## Решения, принятые агентом (мелкие, обратимые)

- **Временный приёмник до 05 — RAW, а не YUV-заглушка из плана.** Для подтверждения 60 к/с нужен именно RAW-поток: режим сенсора HAL выбирает по нему. `AImageReader` с usage `GPU_SAMPLED_IMAGE` (факт 00 C4), кадры сразу отпускаются, CPU пиксели не читает. В коде помечено «ВРЕМЕННО до сессии 05», план 05 обновлён.
- **Поиск вендорских тегов — `ACameraMetadata_getTagFromName` (API 35)**, а не `ACameraManager_getTagFromName`: второй в NDK 30 объявлен только для вендорских сборок (`__ANDROID_VNDK__`). Уточнение записано у решения 37.
- **Где ставятся рычаги частоты — как в зонде 00:** диапазон AE `[60,60]` — и в параметрах сессии, и в каждом запросе; ключи CamX — только в запросе, без диапазона AE.
- **Политика жизненного цикла:** приложение ушло в фон → камера отпускается (Android не даёт камеру фоновым, а Oplus замораживает фоновые процессы); вернулось → движок восстанавливает желаемое. Только отладочный сценарий `camera-evict` на время своей работы включает «держать камеру в фоне» — иначе настоящего вытеснения не увидеть. Маршрутизатор гарантированно возвращает обычную политику при любом исходе сценария.
- **Продукт пока сам камеру не открывает**: видоискателя ещё нет, камеру открывают только сценарии.
- **Порог роли «ширик» — 90°** (был 100° — при замеренных 102° запас 2° хрупок). Порог стоит посередине между основной (72°) и шириком (102°), закреплён тестом на замеренных углах.
- **Гиперфокальное расстояние** — честное «не сообщено» (`Option`), если HAL ключ не дал. Первая версия разбора подставляла туда минимальную дистанцию фокуса — это была бы выдумка.
- **Номер кадра** берётся из `onCaptureStarted` (колбэки V2) по совпадению метки сенсора. Не нашёлся — запасной номер отрицательный, чтобы не совпасть с настоящими, и считается.
- **Строка результата smoke ≤ 4000 байт**: полный каталог и шесть шагов замера в неё не влезали. Отчёт двухслойный: сводка в `FASTICAMERA_RESULT`, полные данные — строками стадий `detail_*`, `smoke_wait.py` печатает их как `FASTICAMERA_DETAIL`.

### Факты телефона (новые)

- **Логическая камера 0 не отдаёт финальных результатов запросов.** На 148 частичных (`onCaptureProgressed`) — 0 финальных (`onCaptureCompleted`); RAW-кадры идут ~29–30 к/с. Java-зонд 00 на той же камере даёт то же (`img_fps 30,01`, `res_fps null`), значит, это поведение HAL, а не NDK. В сценарии это ожидание явное («результаты не шлёт HAL»), а сторож провалит шаг, если прошивка начнёт их слать. **Важно для сессии 13**: переключение объективов через логическую камеру потребует метаданных из частичных результатов или физических камер.
- Углы обзора по длинной стороне сенсора: основная 72,46°, фронт 71,00°, ширик 102,03°.
- В карте HAL больше RAW-размеров, чем знала 00: у логической 0 ещё `raw10 4000×3000`, у фронта ещё 2304×1296 (RAW10 и RAW16).
- На интент `STILL_IMAGE_CAMERA` на телефоне отвечают два приложения (системная камера и стороннее); интент без пакета открывает диалог выбора.
- `ACameraManager_getTagFromName` в публичном NDK 30 закрыт `__ANDROID_VNDK__`; публичный путь — `ACameraMetadata_getTagFromName` (API 35).

## Дефекты, найденные по ходу, и их причины

1. **(ревью, высокая) Вечное зависание потока камеры при закрытии во время потока кадров.**
   - Причина (подтверждена по `frameworks/av/media/ndk/NdkImageReader.cpp`): `AImageReader::close()` берёт замок reader-а и под ним ждёт остановки потока колбэков (`mCbLooper->stop()`). Наш слушатель на этом потоке вызывает `acquireNextImage`/`AImage_delete`, которым нужен тот же замок. Взаимоблокировка — на каждом закрытии, если колбэк в этот момент внутри NDK.
   - Исправлено «воротами» `CallbackGate`: колбэк держит их на всё время работы с NDK, поток камеры закрывает ворота и только потом удаляет reader.
   - Тест гонки на ПК (fake reader, ограниченные ожидания) падает без исправления — проверено откатом.
2. **Smoke `camera-evict` не вытеснял камеру.** Причина: интент `STILL_IMAGE_CAMERA` без пакета открыл системный диалог выбора (`ResolverActivity`) — на телефоне два обработчика интента. Камеру никто не открыл; сценарий честно упал «вытеснения не было».
   - Исправлено: интент адресуется пакету системной камеры, драйвер ждёт запуска (`am start -W`) и проверяет, что открылась именно она. Иначе — ошибка драйвера, а не тихий «проход».
   - Тест на диалог выбора падает без проверки — проверено откатом.
3. **(ревью, средняя) Бесконечный цикл восстановления**, если платформа раз за разом закрывает свежую сессию. Причина: счётчик попыток обнулялся сразу после успешной перенастройки. Теперь он обнуляется только после `recovery.stable_frames_before_reset` (30) кадров стабильного потока, а повтор идёт с задержкой. Тест «сессия закрывается после каждой настройки → `RecoveryExhausted` после 5 попыток» падает без исправления.
4. **(ревью, средняя) Вечное ожидание «камера свободна».**
   - При `TooManyCamerasOpen` сигнала доступности нашей камеры нет (лимит общий) — теперь повтор по таймеру.
   - Сигнал «свободна» мог прийти раньше «отключена» (разные потоки NDK) и потеряться. Теперь движок помнит последнюю доступность и сравнивает её с моментом последней попытки открытия.
   - Оба теста падают без исправлений.
5. **(ревью) Use-after-free контекста состояния сессии.** `onClosed` вызывается из деструктора сессии на потоке последнего владельца (`ACameraCaptureSession.cpp`) и может прийти после разрушения бэкенда. Теперь эти контексты (~100 байт на сессию) намеренно не освобождаются до конца процесса и считаются в диагностике — как контекст доступности.
6. **(ревью) Мелкие:**
   - потолок частоты считался делением вниз (16 666 667 нс → 59 к/с) — теперь сравнение длительностей с допуском 1 мкс;
   - команда, отправленная между «стоп» и «остановлен», молча терялась — теперь `EngineStopped` у отправителя;
   - запасные номера кадров могли совпасть с настоящими — теперь отрицательные.
7. **Порог роли «ширик» 100° при замеренных 102°** — хрупкий запас, найден на первом smoke. Порог 90° закреплён тестом на замеренных углах: со старым порогом тест падает.
8. **Выдуманное гиперфокальное расстояние** при отсутствии ключа (подмена минимальной дистанцией) — заменено честным «не сообщено».

## Тесты

**Rust: 907 на ПК** (было 571).
- `camera-contract` — 18 тестов: инварианты каталога, роль/ID, длительность кадра ↔ 60 к/с = 16 666 667 нс, угол обзора, коды EXIF.
- `camera-core` — 102 теста:
  - машина состояний на fake: каждый переход с журналом вызовов бэкенда;
  - **вытеснение во время `Configuring`** → `Evicted` → `Available` → поток → `Recovered{Evicted, 1}`;
  - **`ERROR_CAMERA_SERVICE` при `Streaming`** → повтор по таймеру не раньше срока → `RecoveryExhausted` после лимита;
  - **повторное `open` той же камеры** → `AlreadyInState` и ни одного вызова бэкенда;
  - **`switch_to(Tele)`** → `Unsupported(RoleNotPresent)`, ничего не изменилось;
  - события чужого поколения отбрасываются; фон и передний план;
  - ящик: 1000 кадров при застрявшем движке вытесняют старые со счётчиком, а «отключено» среди них не теряется;
  - настоящий поток: паника бэкенда → `EnginePanicked`, команды дальше отвечают; `shutdown` с таймаутом;
  - темп на числах 00; роли на фикстурах и замеренных углах; конфиг.
- `camera-android` — 90 тестов:
  - числа основной камеры OnePlus 11 → ровно ожидаемые возможности;
  - логическая камера; отсутствующие и битые ключи — разные ошибки;
  - реестр тегов: нет тега → `Unsupported`, неверный тип → ошибка, запись не трогает чужие ключи, на камерах 0/1/3 HAL об именах CamX даже не спрашивается;
  - выбор рычага: 16:9@60 → AE, основная 4:3@60 → CamX 16 666 667 нс, ширик 4:3@60 → AE даже при найденных тегах;
  - план запроса; коды NDK; ворота и сток reader-а; номера кадров.
  - Плюс сверка всех чисел тегов с bindgen при сборке под Android: подмена значения роняет сборку — проверено.
- `camera-ndk-sys` — 14 тестов: поиск NDK и libclang, понятные ошибки.
- `fasticamera-app` — 264 теста:
  - политика жизненного цикла через настоящий маршрутизатор и fake-движок, возврат политики при успехе, провале, панике и вытеснении сценария;
  - три сценария на всей матрице исходов, включая «факт изменился»;
  - каждая строка результата и стадии ≤ 4000 байт.

**Скрипты: 277** (было 210): проверки трёх сценариев, разбор `dumpsys media.camera` на синтетической фикстуре (каждое поле расхождения отдельно), шаг запуска системной камеры (команда, диалог выбора → ошибка), сквозной прогон стадий драйвера.

**Проверено временным откатом** (сломал → тест упал → вернул): проверка поколения устройства; порог `RecoveryExhausted`; вытеснение старейшего кадра из ящика; `AlreadyInState` при повторном `open`; таймер раньше срока; CamX на любой камере; ключи CamX в параметрах сессии; расход пары «метка → номер»; `active_array` как right/bottom; подмена чисел тегов (сборка); ворота reader-а; ранний сброс счётчика попыток; «свободна раньше отключена»; `TooManyCamerasOpen` в ожидании; потолок частоты; команда после «стоп»; запасные номера кадров; утечка контекстов; возврат политики в маршрутизаторе; ожидание подтверждения `close` между шагами; сторож «финальных результатов нет»; проверка диалога выбора; порог ширика.

Не покрыто автотестами на ПК (с причиной): Android-слой `camera-android/src/android/` — на ПК нет NDK. Его проверили три smoke-сценария сквозным путём. Нейтральная логика (ворота, сток reader-а, учёт утечек, разбор метаданных) вынесена и протестирована на ПК.

## Известные ограничения

- **Android-слой проверен только smoke-сценариями** (5–10 с на камеру); длительный прогон с теплом — сессия 05 (5 минут 4K60 в критерии выхода).
- **Автооткат 4:3@60 → 30 при неработающих ключах CamX** (решение 23) — сессия 05. Сейчас без тегов режим честно `FrameRateNotAchievable`.
- **Логическая камера 0 без финальных результатов** (факт выше) — решать в сессии 13.
- **`onDisconnected` всегда трактуется как вытеснение.** NDK не различает «отняли», «отозвали разрешение» и «отключили». На телефоне подтверждено именно вытеснение.
- **Контексты состояния сессий не освобождаются до конца процесса** (~100 байт на каждую конфигурацию) — осознанно, против use-after-free; счётчик в диагностике.
- **Команды, уже лежащие в очереди в момент остановки движка, не получают ответа** — только учёт и предупреждение в логе (остановка — конец процесса).
- **Smoke вытеснения работает в отладочном режиме «держать камеру в фоне».** Обычная политика «фон → отпустить → вернуться → поток» проверена на ПК через маршрутизатор, на телефоне отдельным сценарием не гонялась.
- **Для `camera-stream`/`camera-evict` разрешение камеры должно быть выдано, экран разблокирован.**
- `scenario/mod.rs` — 702 строки (мягкий предел 700). Это 11 строк регистрации; ужать можно только косметической правкой чужого кода (правило 8 `AGENTS.md`). Следующий сценарий — повод вынести реестр.

## Задел V1–V10

- **V2:** `SensorTimestamp` — отдельный тип в шкале `CLOCK_BOOTTIME`; темп считается только по нему, `SENSOR_FRAME_DURATION` хранится лишь для отчёта (в режиме CamX он ложный).
- **V7:** движок различает «перестраиваюсь» (`Reconfiguring`) и «недоступна». `switch_to` переносит режим и поток на другую камеру. Бесшовность — сессия 13; факт про логическую камеру 0 — её вход.
- **V10:** `PER_FRAME_CONTROL` пока не используется; ручная экспозиция идёт через план запроса.
