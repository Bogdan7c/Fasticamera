# Сессия 01: скелет репозитория, сборки и проверок — отчёт

**Статус: выполнена.** Из чистой копии репозитория `scripts/ci-checks.sh all` = 0. Пустое приложение ставится на телефон одной командой, грузит Rust-библиотеку и пишет в logcat. Smoke-сценарии `hello` и `panic` проходят на телефоне.

- Дата: 25 октября 2026, вечер.
- База: `8459f12`. Итог: незакоммиченные изменения (коммит — по команде владельца).
- Телефон: OnePlus 11 CPH2447, Android 16, беспроводной `adb`.

## Коротко, простыми словами

1. Появился «каркас» проекта. Это Rust-workspace из двух crate-ов (`camera-contract` — пустой словарь на будущее, `fasticamera-app` — нативная библиотека приложения) и Android-проект, который сам собирает Rust и кладёт его в APK.
2. Правила проекта теперь проверяет скрипт, а не память агента. Одна команда `scripts/ci-checks.sh all` гоняет формат, линтер (для ПК и для телефона), тесты, проверку границ между модулями, лимит размера файлов и сборку обоих APK.
3. На телефоне две иконки: «Fasticamera debug» и «Fasticamera». Их можно держать рядом и сравнивать.
4. Логи Rust идут в logcat под тегом `Fasticamera`. Уровень задаётся конфигом и меняется на один запуск без пересборки. Если Rust «паникует», в logcat попадают файл, строка и сообщение, а приложение не падает молча (решение владельца).
5. По ходу найдены и исправлены два настоящих дефекта (см. «Дефекты»). Один из них — в моём же скрипте ожидания результата.

## Решения владельца (сессия 01)

1. **AGENTS.md**: в правиле размера модулей crate-ы Fastiplayer заменены на crate-ы Fasticamera (`camera-core`, `camera-android`, `isp-vulkan`, `ui-render-vulkan`, `camera-screen`, `fasticamera-app`). Отдельным «да» заменены и примеры плеера в разделе «Architectural rules for new features» (`player-core`, `PlaybackPipeline`, методы декодера) на модули и намерения камеры из README плана.
2. **Паника ловится на границе Rust ↔ Kotlin.** В logcat пишется место и сообщение, Kotlin получает отчёт. Не `panic = abort`.
3. **Debug и release стоят рядом**: `dev.fasticamera.debug` и `dev.fasticamera`.
4. **Мост «tracing → logcat» — свой** (~150 строк). Готовые мосты (`tracing-logcat`, `paranoid-android`, `tracing-android`) молодые, у каждого один автор, обновлялись в 2022–2024.

## Решения, принятые агентом (мелкие, обратимые)

- Release подписан debug-ключом: приложение личное, сменить ключ потом — одна переустановка.
- R8 в release выключен: Kotlin-кода почти нет.
- Конфиг нативной части фиксирован на процесс: повторный `initialize` с другим конфигом не меняет его, а сообщает `requested_differs: true`. Скрипты запускают Activity с `-S` (свежий процесс).
- Фильтр логов обязан содержать уровень по умолчанию. Иначе опечатка `debgu` молча выключила бы все логи: `Targets` принял бы её за имя цели.
- Ревизия сборки — `sha` плюс `-dirty`, если есть **любые** изменения, включая неотслеживаемые файлы. `git describe --dirty` их не видит, и первая версия выдавала сборку с новыми файлами за чистый коммит.
- Зонд `tools/device-probe` остаётся отдельным проектом вне workspace и вне `ci-checks` (у него свои проверки из 00). Ratchet его файлы видит.

### Как устроена нативная часть

- Kotlin только маршрутизирует. `MainActivity` собирает конфиг (BuildConfig + intent-параметр `log_filter`) и вызывает `NativeBridge.initialize(json)`, а если в intent есть `scenario`, то `NativeBridge.runScenario(name)`. Ответ показывается на экране.
- Каждый JNI-экспорт выполняется через `jni_boundary::run_guarded`. Паника становится `PanicReport { message, location, thread }`. Сбой самого JNI становится `RuntimeException` в Kotlin, а не молчаливой пустой строкой.
- Логирование: реестр `tracing-subscriber` + свой слой `SinkLayer` + фильтр `Targets` из конфига, приёмник — logcat (stderr на ПК). Длинные записи режутся по 4000 байт по границе символа, NUL внутри текста становится видимым `\0`. Отказы logcat считаются и попадают в отчёт `hello` (`log_write_failures`): ниже логов канала нет, поэтому молчать нельзя.
- Мимо фильтра пишутся только отчёт о панике (уровень FATAL) и строка `FASTICAMERA_RESULT`. Так `log_filter=error` не ломает smoke-проверку.

### Guardrail границ crate-ов

- Граф берётся из `cargo metadata` с полным resolve и без фильтра платформы. Ловятся и транзитивные, и android-only зависимости. Dev-зависимости осознанно не считаются.
- Каждый crate workspace обязан быть классифицирован по роли. Будущие crate-ы из README перечислены заранее.
- Правила: нейтральные ядра не зависят от Android/Vulkan; `camera-contract` — лист; `ui-render-vulkan` не знает про камеру; `camera-screen` не вызывает Camera2 и не рисует; `gpu-vulkan` не знает про камеру и ISP; `camera-android` не знает про UI, Vulkan и ISP; от `fasticamera-app` никто не зависит.
- Проверено вживую на копии workspace: `camera-contract` с android-only зависимостью `jni` даёт код 1 и сообщение `camera-contract → jni: запрещено правилом neutral-no-platform (…)`, а также цепочку до `jni-sys`.

## Дефекты, найденные по ходу, и их причины

1. **Гонка при установке логирования.** Тест `runtime` падал нестабильно. Причина: проверка «подписчик ещё не стоит?» и `set_global_default` были раздельными шагами. Два одновременных `initialize` давали второму ложную ошибку «подписчик чужой». Исправлено: проверка и установка — одна операция `OnceLock::get_or_init`. Пять прогонов подряд зелёные.
2. **Smoke-скрипт не видел строку результата, хотя она была в logcat.** Причина в `scripts/smoke_wait.py`: готовность ждалась через `select` по дескриптору, а `readline` забирал в буфер Python сразу пачку строк. Дескриптор пустел, и `select` ждал до таймаута. Исправлено: строки читает отдельный поток, основной ждёт очередь с дедлайном. Регрессионный тест (подпроцесс пишет пачку строк и не закрывает вывод) **падает на старой реализации** — проверено временным откатом — и проходит на новой.
3. **Сборка с новыми файлами выдавала себя за чистый коммит** (`git describe --dirty` не видит неотслеживаемые файлы). Исправлено: `-dirty` считается по `git status --porcelain`. На телефоне теперь видно `8459f126d11e-dirty`.
4. **Текст уезжал под статус-бар.** Причина: targetSdk 36 рисует окно под системными панелями (edge-to-edge обязателен). Исправлено: тема без ActionBar и отступы по `WindowInsets`.

Наблюдение без доказанной причины. В первых ручных попытках `adb logcat -d` уже через несколько секунд после запуска не находил строк `Fasticamera`. В это время телефоном активно пользовались. Самое вероятное объяснение — вытеснение из буфера `main` в 256 КиБ (тот же эффект, что дефект 1 сессии 00). После исправления дефекта 2 потоковое чтение с `-T` стабильно видит все строки во всех последующих прогонах (9 из 9). Буфер не трогали: `logcat -G` — изменение системы.

## Тесты

**Rust (35 на ПК без фич + 35 со всеми фичами)**:
- конфиг: валидный, лишнее поле, неизвестный тип сборки, пустой фильтр, опечатка уровня, неверный уровень в директиве;
- логирование на настоящем подписчике с собирающим приёмником: событие доходит с целью, сообщением и полями; фильтр по уровню; директива для отдельной цели; кавычки у строковых полей; нарезка длинного текста без разрыва UTF-8; видимый NUL; соответствие уровней; C-тег = публичный тег;
- паника: отчёт с сообщением и точным `файл:строка` из теста; отчёт не переиспользуется следующим вызовом; запасной путь без места;
- runtime: первая инициализация, повтор с тем же и с другим конфигом (действует первый), неверный конфиг не меняет состояние и позволяет повторить;
- сценарии: `hello` проходит и сообщает версию, ABI, тип сборки и фильтр; неизвестный сценарий даёт список доступных; вызов до `initialize` — явный отказ; `panic` без фичи даёт «только в debug», с фичей — `panicked` с местом в `intentional_panic.rs`;
- строка результата: префикс и JSON туда-обратно; слишком длинный отчёт заменяется отчётом об ошибке в пределах лимита.

**Скрипты (60)**:
- guardrail (16): end-to-end на настоящем `cargo metadata` по фикстурам-воркспейсам с фейковыми `jni`/`ndk`: запрещённая зависимость даёт код 1 и цепочку; разрешённая — 0; android-only ловится; dev-only не считается; неклассифицированный crate — 1; битый TOML и неизвестная роль — 2; настоящий файл правил валиден;
- ratchet (24): 801 строка — ошибка; 750 — предупреждение; рост legacy-файла — ошибка; `--update-baseline` только уменьшает и не узаконивает новые большие файлы; `target/` и `build/` не сканируются; битая политика — 2;
- smoke (20): вердикты `hello`/`panic` (неверный ABI, нет ревизии, `failed`, чужой сценарий пропускается, нет результата → 3, битый JSON, падение процесса, паника без записи хука, паника не в том месте, `panic` в release); чтение живого потока (регрессия дефекта 2) и дедлайн; `device-smoke.sh` с фейковым `adb`: нет устройства → **2** «устройство не найдено», чужая модель → 2, два телефона → 2 с подсказкой `ANDROID_SERIAL`, нет сценария → 64, неверный вариант → 64.

## Известные ограничения

- Smoke-сценарий проверяет загрузку библиотеки и логирование, но не камеру и не Vulkan: они появятся в 02–05.
- Хук паники пишет место и сообщение без стека: на Android `RUST_BACKTRACE` не задан. Для падений есть `ndk-stack` и символы.
- Имя потока у главного потока Android с точки зрения Rust — `<без имени>`.
- shellcheck не установлен: CI проверяет bash только `bash -n`. Поставить ли его (пакет системы) — на усмотрение владельца.
- Serena: в `.serena/project.yml` не заданы языковые серверы, поэтому символьные инструменты по Rust/Kotlin пока не работают. Включить rust-analyzer — отдельная маленькая правка конфигурации, предлагаю сделать в 02.
