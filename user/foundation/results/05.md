- Дата: 27 октября 2026.
- База: `7d1aa03`. Итог: коммит «Сессия 05» в `main` (решение 44: коммит и push сразу после закрытия сессии).
- Телефон: OnePlus 11 CPH2447, Android 16, беспроводной `adb`.

## Коротко, простыми словами

1. **Кадр камеры доходит до экрана без единой копии.** Буфер с сенсора отдаётся видеокарте «под расписку» (лизинг) и возвращается камере только тогда, когда видеокарта его дочитала (fence). На экране — отладочная картинка мозаики в ложных цветах: это ещё не ISP, а доказательство, что кадр дошёл.
2. **Счётчик копий честный.** В обычном прогоне `cpu_copies_per_frame = 0`. Отладочный сценарий нарочно копирует каждый кадр через CPU — счётчик показывает ровно 1,0 на кадр. Значит, ноль — настоящий ноль, а не неподключённый счётчик.
3. **Чужие метаданные к кадру не приклеиваются.** Кадр и результат запроса (время, выдержка, ISO и т.д.) склеиваются только по точному совпадению метки сенсора. Нет пары — кадр уходит с честной пометкой «метаданных нет», а не с данными соседа.
4. **Пять минут 4K60 RAW — без сбоев и без нагрева.** Тепловой статус «нет» в начале и в конце, запас по теплу даже вырос (0,58 → 0,67), батарея +1,7 °C.
5. **Если вендорских ключей 60 к/с нет, камера честно откатывается на 30** и сообщает об этом событием (решение 23).
6. **Задержка «сенсор → экран» измерена и разложена**: ~30 мс — камера (экспозиция, считывание, HAL), остальные 37–54 мс — наш показ (очередь swapchain и линия кадра Android). Это вход для оптимизации в 07, а не дефект.

## Решения, принятые агентом (мелкие, обратимые)

- **Паспорт кадра — две части**: постоянная (`StreamPassport`: формат, размер буфера, полезная область, мозаика, уровни, вендорская обработка, ориентация, частота и рычаг) одна на сессию, кадры делят её через `Arc`; покадровая — результат запроса + цветовые подсказки (динамический black/white level, `COLOR_CORRECTION_GAINS`, neutral point).
- **Полезная область 16:9** = строки `0..ширина×9/16` (факт 00 C2 для основной камеры; для ширика 16:9 не измерено — записано в коде).
- **Ориентация сенсора — поле `CameraCapabilities::sensor_orientation`** (нужна отладочному показу; пригодится ISP и UI).
- **`AHardwareBuffer` между камерой и GPU — `BorrowedHardwareBuffer<'a>`** в `shell-contract` (как `BorrowedFd` в std): заимствование привязано ко времени жизни лизинга, GPU при импорте берёт свою ссылку NDK.
- **Fence-ы нескольких потребителей сливаются `sync_merge`**; сбой слияния — утечка буфера со счётчиком (решение 43), а не возврат с неполным fence.
- **Reader закрытой сессии не удаляется, пока хоть один его кадр на руках** («отставка»), иначе `AImageReader_delete` освободил бы буферы под GPU. Удаление — лениво на потоке камеры; при остановке ждём ограниченно (`retired_reader_drain_timeout_ms`), дальше — утечка со счётчиком.
- **Рендер возвращает показанный кадр с fence следующего сабмита**, в котором его уже нет. Это корректно по спецификации: первая область синхронизации сигнала семафора в `vkQueueSubmit2` включает все команды, раньше по порядку отправки (сверено через Context7).
- **Владение буфером между очередями**: забрать у камеры (`QUEUE_FAMILY_FOREIGN`) — один раз при первом чтении, вернуть — один раз в сабмите, который его заменил (ревью, дефект 2).
- **Рендер на Android всегда в режиме показа камеры**; без потока рисует чёрное (тестовый градиент 03 продуктом больше не показывается; сценарии `render`/`render-lifecycle` судят ритм, а не картинку — проверено на телефоне).
- **Перед замером и скриншотами — 1,5 с на установление автоэкспозиции** (`viewfinder_settle_ms`, дефект 1).
- **`raw_reader_max_images` удалён из конфига**: `maxImages` теперь считает план пула (`PoolPlan`): ячейка видоискателя 1 + у рендера 2 + ожидание пары 2 + кольцо + очереди «ни одного молча» + запас 1 = **6** по умолчанию. На телефоне за 5 минут на руках было максимум 4.

### Путь кадра

```
сенсор → AImageReader (usage GPU_SAMPLED_IMAGE, maxImages из плана пула)
  колбэк reader-а: acquireNextImageAsync → кадр + acquire-fence → RawFrameProducer::offer_frame
  колбэк результата: CaptureCompleted → движок (темп) и offer_capture_result (паспорт)
  хаб: пара по SENSOR_TIMESTAMP → раздача: видоискатель (самый свежий) / кольцо / «ни одного молча»
поток рендера: poll_latest → импорт AHB (кэш по id) → мозаика → present + экспорт fence
  прежний кадр → release_after_gpu_fence(fence) → sync_merge → AImage_deleteAsync → буфер у камеры
```

Движок камеры в пути кадров не участвует: он получает только результаты запросов для темпа. Никто никого синхронно не ждёт.

Release (60 с): камера та же (29,4 мс), а задержка на экран **выше** — p50 83,4 мс, p95 90,5. Наша часть = 37 мс в debug и 54 мс в release, то есть на кадр больше.
- Причина по устройству темпа (03): рендер просыпается по тику vsync, берёт самый свежий кадр и целится в показ по линии кадра Choreographer — на 2–3 vsync вперёд. Кадр камеры приходит с постоянной фазой относительно vsync; если чуть позже тика — ждёт следующего (+0…16 мс).
- Почему release хуже — **гипотеза**: release просыпается точно на тике и «промахивается» по фазе, debug медленнее и успевает. Прямого замера фазы нет.
- Что делать — в 07: брать кадр камеры как можно позже перед сроком сдачи композитору и выбирать ближайшую выполнимую линию кадра.

**Загрузка GPU не измерена**: счётчики Adreno в sysfs без root закрыты (`Permission denied`). Отладочный шейдер мозаики тривиален; бюджет полного кадра (V4) — сессия 07 через Perfetto/AGI.

**3,1 % кадров видоискатель пропускает** (`dropped_superseded`, столько же повторных показов): камера (60,04) и экран (60,00) — два независимых генератора, фаза медленно плывёт. Для видоискателя это норма `LatestWins`; для записи (план `video`) кадры идут потребителю «ни одного молча», которому видоискатель не мешает (V1).

## Дефекты, найденные по ходу, и их причины

1. **(телефон) Первый скриншот «чёрный» (0,22 из 255), второй нормальный.** Причина: стадия для скриншотов наступала на самом первом показанном кадре, а автоэкспозиция HAL после старта ещё не сошлась — кадр почти чёрный (0,7 в области кадра), через 1,5 с — ~70–120. Исправлено фазой установления `viewfinder_settle_ms` (1,5 с) перед замером и скриншотами; заодно окно замера больше не включает разгон AE. Тест падает без исправления — проверено откатом.
2. **(ревью) Барьеры владения при повторном показе кадра.** Каждый кадр, даже показанный повторно, заново «забирался у камеры» (переход из `UNDEFINED` без зависимости от предыдущего сабмита) — формально гонка записи раскладки с чтением прошлого сабмита. Исправлено: забрать один раз при первом чтении, вернуть один раз в сабмите-заменителе (`ownership.rs`). Тест падает без исправления.
3. **(ревью) Синхронное ожидание GPU на каждом кадре после сбоя экспорта fence** — нарушение инварианта 4. Исправлено: кадр отпускается, когда номер завершённых сабмитов (fence слота) перешёл за последний сабмит, который его читал; пересоздание семафора — с паузой в кадрах и лимитом попыток, без ожиданий. Тесты падают без исправлений.
4. **(запуск release) `raw-stream` в release не дошёл до потока** — у release-пакета `dev.fasticamera` не было разрешения камеры; движок честно встал в `error`. Не дефект кода: разрешение выдано нашему пакету (`pm grant`, решение 30).

## Тесты

**Rust: 1138 на ПК** (было 907; со всеми фичами). Главное:
- `raw-frame-stream` — 34: спаривание (оба порядка, 10 вперемешку, «метки на 1 нс разные не спариваются», потерянный результат ровно на таймауте, потерянный кадр, переполнение ожидания), эпохи, `LatestWins` / `KeepLast` / `NeverDropSilently` (брак с номером кадра), возврат буфера только после всех держателей и сигнала всех fence-ов (настоящие fd), утечка при забытом лизинге, план пула, 2000 кадров из двух потоков.
- `camera-android` — 135: слив reader-а (исчерпание пула ровно один раз, ворота), слияние fence-ов (сбой на 1-м/2-м слиянии, каждый fd закрыт ровно раз), отставка reader-ов, паспорт на фикстурах OnePlus 11 (16:9 → 4096×2304 сверху), ориентация, цветовые подсказки, «возраст кадра».
- `camera-core` — 114: откат 60 → 30 (две настройки, `StreamDegraded` до `StreamConfigured`, цель темпа 30), откат не на тот сбой — нет, повтор отката невозможен.
- `gpu-vulkan`: мозаика против CPU-эталона в ±1 (все 4 CFA, нормировка, полезная область 16:9 с мусором ниже, поворот + вписывание, RAW10 с выравниванием строк), хук сабмита (fence позднего сабмита покрывает ранние), повторный показ без барьеров = та же картинка.
- `render-loop`: функциональный тест — настоящий поток кадров + настоящий рендер на RADV: кадры доходят до показа, ни один буфер не возвращён раньше сабмита, который перестал его читать, после остановки всё возвращено, утечек 0, объекты Vulkan вернулись к исходным, ошибок validation 0; план владения, учёт лизингов, восстановление экспорта.
- `fasticamera-app`: сценарии через настоящий маршрутизатор с fake-камерой и fake-рендером — каждое правило вердикта, порядок стадий, установление AE, проба CPU выключается при любом исходе, размер строки результата; жизнь reader-ов в `camera-stream`.

**Скрипты: 336** (было 277): разбор `screencap` (заголовки 12 и 16 байт, форматы пикселей), анализ «чёрный / неподвижный / живой», шаг драйвера, проверки трёх сценариев, сквозной вердикт.

**Проверено временным откатом** (сломал → тест упал → вернул): спаривание без сравнения меток; исходный лизинг публикации не отпущен; таймаут `<` → `<=`; порядок кадров в ячейке; индекс сбоя слияния fence-ов; `note_pool_exhausted`; удаление reader-а без учёта кадров на руках; высота 16:9; тег WB; понижение частоты и запись желаемого режима при откате; порядок освобождения в рендере; строки CFA, `valid_top`, направление поворота, сдвиг RAW10, вычитание black, шаг строки RAW10; забор у камеры при повторном показе; проверка «после завершения сабмита»; защита семафора; правило CPU-копий; проверка возрастания номеров кадров; запись «возраста кадра»; фаза установления AE.

Не покрыто автотестами на ПК (с причиной): настоящий импорт AHB, барьеры `QUEUE_FAMILY_FOREIGN`, `sync_merge` и `AImage_deleteAsync` — на ПК нет NDK и внешней очереди. Их проверили сценарии на телефоне сквозным путём (validation в debug — 0 ошибок).

## Известные ограничения

- **Задержка «сенсор → экран» 67–83 мс**, из них наша часть 37–54 мс (очередь показа и фаза тика). Оптимизация — 07.
- **Загрузка GPU не измерена** (sysfs Adreno без root закрыт) — 07, Perfetto/AGI.
- **После отката 4:3@60 → 30 желаемым режимом остаётся 30**: при переключении на ширик, где 4:3@60 работает штатно, частота останется 30, пока экран не попросит 60 снова. Переключение камер — сессия 13.
- **Сбой `sync_merge` (кончились дескрипторы) — утечка буфера** со счётчиком: место в пуле не возвращается до конца процесса (решение 43). На телефоне сбоев 0.
- **После исчерпания пула кадры берутся от старых к новым** (`acquireNextImage`): старые доходят до видоискателя и вытесняются. Исчерпаний на телефоне 0.
- **Reader прошлой сессии живёт, пока рендер не получит первый кадр новой** (рендер держит последний показанный) — это задержка освобождения памяти, не безопасности.
- **Полезная область 16:9 измерена только на основной камере**; для ширика — предположение, записано в коде.
- **Реальные кадры на экране тёмные**: отладочная мозаика линейная, без гаммы и баланса белого — так и задумано (это не ISP). Пороги скриншота в `scripts/smoke_screen.toml` выставлены по физике и подтверждены прогонами (яркость 7–34 при пороге 2).
- `camera-stream`: допуск «кадров на руках» берётся из плана пула с кольцом на верхней границе (приложение не видит точный план) — осознанное приближение.

## Задел V1–V10

- **V1** — выполнен: один RAW-поток, три политики; запись проверена тест-потребителем «ни одного молча» (брак = счётчик + событие с номером кадра).
- **V2** — паспорт кадра: время начала экспозиции (BOOTTIME), длительность, перекос rolling shutter; сдвиг BOOTTIME↔MONOTONIC измеряется для задержки показа.
- **V5** — рендер принимает внешний кадр без копии и отдаёт fence; входная surface кодера подключается тем же путём (03).
- **V9** — кольцо `KeepLast(N)`: N = бюджет памяти / размер кадра, с потолком; по умолчанию 0 (решение 41).
