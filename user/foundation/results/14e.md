# Сессия 14e: уже снятый снимок доживает до файла при пропаже поверхности экрана

**Статус:** закрыта 22 ноября 2026. База — `32817ea`, итог — коммит этой сессии.

## Коротко, простыми словами

1. **Раньше** свернул приложение или погасил экран посреди серии — и снимки, которые уже «щёлкнули», могли пропасть. Причин было две:
   - без экрана поток рендера засыпал без срока, а снимки двигаются только его шагами;
   - отсоединение экрана само бросало все недоделанные снимки и при этом ждало GPU, сверх бюджета квитанции.
2. **Теперь** поток рендера, пока снимки ждут итога, просыпается сам примерно раз в кадр (16 мс) и делает те же шаги, что с экраном. Бросаются только снимки, которые ещё не выбрали кадр с экрана: им без экрана выбирать нечего, они получают честный отказ.
3. **На телефоне** серия из 5 нажатий и сразу HOME: 4 снимка были в работе, все 5 файлов сохранились за ≈ 1,5 с. С погашенным экраном — тоже все 5. Под validation layer — 0 ошибок.
4. **Попутно найдено:**
   - причина рывка до 62 мс в серии: мастерская снимка делает работы строго по одной, это уходит в 16a (решение 152);
   - память процесса растёт от серии к серии, но упирается в потолок ≈ 480 МБ, в фоне освобождается всё;
   - 75 мс из 14c не повторились.

## Решения владельца (сессия 14e)

- **150** — снимки без экрана двигает сам поток рендера по таймеру. Отдельный поток снимков отклонён: две нити делили бы одну очередь GPU.
- **151** — заморозка или убийство процесса во время записи остаются известным ограничением; foreground-служба «сохраняю фото» уходит в бэклог.
- **152** — блокировка «голова очереди» в мастерской снимка уходит в 16a.

Подробности — README плана, решения 150–152.

## Что изменилось (по модулям)

Всё в `render-loop`, соседи не правились.

- **Граница рендера** `still.rs`: `StillWorkload::{Idle, Unfinished}`, то есть «есть ли снимки, ждущие итога».
- **`DisplayBackend`** (`backend.rs`), два intent-метода:
  - `still_workload()` — только читает, по умолчанию `Idle`;
  - `abandon_stills()` — явный отказ от снимков при неисправности потока, по умолчанию ничего.
  
  `advance_stills` теперь зовётся и без показа.
- **Поток рендера:**
  - новый модуль `thread/worker/still_steps.rs`: `wait_limit_without_presentation`, `advance_stills_without_presentation`;
  - в `worker.rs` только две точки вызова и `abandon_stills` в `enter_fault`. Файл 739 строк, выше мягкого предела 700 (предупреждение ratchet, не ошибка); логика вынесена, в нём +10 строк.
- **Движок снимков**, новый модуль `still/engine_surface.rs`:
  - `on_detach` бросает только `Choosing` и `AwaitingCapture` (`NotSecured(RendererStopped)`), остальное оставляет и не ждёт GPU;
  - `workload()`;
  - `release_gpu_if_drained_without_surface` — без surface опустевшая очередь отпускает GPU;
  - `retire_gpu` — общий разбор GPU, им же теперь пользуется `ensure_gpu`;
  - `SurfaceLink::{Attached, Detached}`: первая лента видоискателя ставит `Attached`.
  
  `advance()` после шагов отпускает GPU, если очередь без экрана опустела. Инварианты модуля (`mod.rs` п. 4, `engine.rs` п. 5) переписаны.
- **Бэкенд Vulkan:** `detach` больше не ждёт GPU снимков, `still_workload`/`abandon_stills` реализованы. `Begin` без surface по-прежнему получает отказ сразу: выбрать «кадр с экрана» нечего. `Target` без surface принимается.
- **Конфиг:** `still.step_interval_without_display_ms` = 16 (1…1000, `[estimate]`: период кадра при 60 Гц, решение 36). Темп проявления без экрана тот же, что с экраном.
- **Счётчики:**
  - `StillDiagnostics.continued_without_surface` — сколько снимков пережили отсоединение;
  - `gpu_released_without_surface`.

## Причина дефекта (решение 146)

Корень не в тепле.

1. `RenderWorker::run_iteration` без показа звал `wait_for_events(None)`, то есть спал без срока. Шаги снимков были только в `render_frame` после показанного кадра. Без surface и на паузе снимки не двигались вовсе.
2. `VulkanDisplayBackend::detach` → `StillEngine::on_detach` → `abandon_all` бросал все снимки, включая захваченные (`Failed(Abandoned)`). Перед этим он ждал GPU (`VulkanStillGpu::abandon`, до `teardown_timeout`). Это третье ожидание сверх двух, которые учитывает бюджет `release_receipt_budget_ms` (`worst_case_wait_before_release_ms` = acquire/teardown + teardown).

Единичный случай 14c «рендер остановлен до конца проявления» — это путь 2, как только surface уходит посреди проявления. Был ли в том прогоне HOME, погасший экран или системное событие, не установить: лога нет.

## Известные ограничения

- **Заморозка процесса** (решение 151). Если система заморозит процесс посреди записи, сроки к разморозке истекут, и такой снимок получит честную ошибку. Если процесс убьют, черновики уберёт уборка при следующем запуске. Серия обычно дописывается за секунды, а заморозка наступает через ≈ 70–100 с (замер на зарядке, с включённым экраном).
- **Экран камеры на паузе не тикает.** Его собственные сроки (`saving_timeout_ms` 45 с) идут по кадрам UI. Если вернуться позже чем через 45 с после нажатия, экран может засчитать уже сохранённый снимок как потерянный: вибрация ошибки и счётчик `lost_captures`. Файл при этом цел. Не проверялось; это косметика экрана, не потеря снимка.
- **На паузе при живой surface** GPU снимков после опустевшей очереди не отпускается. Так было и до 14e. Отпускается только без surface.
- **`zoom` на горячем телефоне красный** и на базе (см. выше), это не тема 14e.
- **Запуск показа в кодер 75 мс (14c)** не воспроизведён, причина не доказана.

## Self-review

- **Отсоединение больше не ждёт GPU** (бюджет квитанции). Исключение — пустая очередь: тогда GPU снимков разбирается сразу, но он простаивает, и остановка возвращается без ожидания, как до 14e.
- **Ровно один итог** сохраняется на всех путях:
  - не захваченные — `finish` в `on_detach`;
  - захваченные — обычные шаги;
  - неисправность — `abandon_stills` → `abandon_all`;
  - остановка — `Drop` движка;
  - запасной путь — `StillEntry::drop`.
- **`step_choosing` и `step_capture_start` без экрана никого не находят:** их стадии брошены в `on_detach`. `prewarm_gpu` без ленты не зовётся.
- **Пробуждения без снимков:** 0, закреплено тестом на настоящем потоке.
- **Тип пробуждения:** `Condvar::wait_timeout` в цикле с пересчётом остатка уже был в `mailbox.rs`. По документации std (Context7) ложные пробуждения обработаны.
- **Ветка «мастерская не запустилась»** (`workshop: None`) без экрана не проверена отдельно. Она ведёт по прежнему пути на потоке рендера, а шаги те же.
