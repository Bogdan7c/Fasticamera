## Коротко, простыми словами

1. **Сырой поток 60 к/с без root есть, причём публичным API.** Достаточно попросить у камеры частоту `[60, 60]`, и HAL сам переключает сенсор основной камеры в режим 4096×2304@60. Кадр приходит в буфере 4096×3072: картинка 16:9 сверху, ниже нули. Пять минут подряд: 18 000 кадров, 60,01 к/с, 5 пропусков, телефон не перегрелся.
2. **4:3 @ 60 тоже есть.**
   - На ширике — родным режимом сенсора 4000×3000@60, публичным API.
   - На основной камере — двумя вендорскими ключами CamX (`disableFPSLimits` + `overrideSensorFrameDuration`): полный кадр 4096×3072 на 60,04 к/с, в том числе с вендорским автоматом экспозиции. Проверено минутой непрерывного потока и содержимым кадров.
3. **Кадр попадает в Vulkan без копий.** Буфер камеры импортируется прямо в GPU (RAW16 как изображение, RAW10 как буфер), compute-шейдер читает его. Контрольная сумма GPU совпала с CPU на каждом кадре.
4. **Готовый кадр из Vulkan уходит прямо в аппаратный HEVC-кодер**: 4K, 10 бит, HLG, 60 к/с, 300 из 300 кадров с ровными метками. Это основа будущей записи видео (задел V5).
5. **Хак с именем пакета не нужен и почти ничего не даёт.**
   - `com.oneplus.camera` ставится, но поведение камеры то же, что у обычного имени.
   - Скрытый телевик (камеры 4 и 5) закрыт фреймворком по разрешению `SYSTEM_CAMERA`, а не по имени.
   - `com.oppo.camera` прошивка не дала установить: проверка подписи.
6. **Нельзя без root**: телевик, полное разрешение 50 Мп, отключение вендорской коррекции виньетирования в RAW.

## C2. Обход потолка 30 к/с (главное)

### Как нашли

1. Источники в сети (сабагент):
   - исходники Qualcomm CamX в зеркалах CAF на GitHub (`tadiphone-caf/vendor_qcom_proprietary`, `camx/src/...`): `manualExposure.disableFPSLimits` с комментарием «allows high frame rate without HFR» и применение `overrideSensorFrameDuration` к frame length lines в `camxsensornode.cpp`. Зеркала старые (до kalama), семантику подтвердили опытом.
   - MotionCam: исходный репозиторий удалён (404), остались форки. По фрагментам README — «до 60 к/с на поддерживаемых устройствах». Деталей кода не получили.
   - XDA и конфиги GCam для OnePlus 11 по теме ничего не дали.
2. Статический разбор системной камеры (`/product/app/OplusCamera`, jadx; декомпиляция только в scratchpad):
   - приложение само не трогает Camera2, всё идёт через вендорский сервис CameraUnit/OCS с режимом сессии;
   - режимы сессии: `0x8021` — видео 60 к/с, `0x8009` — Pro, `0x8001` — фото, `0x80A7` — AI/HDR-видео;
   - `/odm/etc/camera/CameraHWConfiguration.config`: для `0x8021` индекс режима сенсора 4.
3. Таблица режимов сенсора из `dumpsys media.camera` (`org.quic.camera2.sensormode.info.SensorModeTable`):
   - основная: 0: 8192×6144@24, 1–2: 4096×3072@30, 3: 4096×2304@30, **4: 4096×2304@60**, 9: 4096×2304@120, 7: 2048×1152@240 …;
   - ширик: 1: 4000×3000@30, **2: 4000×3000@60**, 4: 4000×2250@60.
4. Типы всех 1057 вендорских тегов — из `dumpsys media.camera` («Vendor tags»). Например, `disableFPSLimits` = byte, `overrideSensorFrameDuration` = int64, `sensor_mode_index` = int32.

### Проверка, что кадры настоящие

Сцена — ванная при свете; анализ каждого 25-го кадра; профиль яркости по 24 полосам по высоте.

- **16:9@60 (режим 4)**: в буфере 4096×3072 заняты **строки 0–2303**, ниже нули. Полосы 0–17 совпадают с полосами 3–20 кадра 4:3. Значит, это **центральная вырезка 4:3 в том же масштабе**, без растяжения. Наш ISP должен обрезать кадр по высоте 2304.
- **4:3@60 на основной через CamX**: заполнены все 3072 строки. Профиль совпадает с 4:3@30 с множителем 0,80, а разница экспозиций (8 мс·ISO800 против 20 мс·ISO400) тоже 0,80. Перекос rolling shutter в режиме 1 — 13,66 мс, это меньше 16,67 мс, то есть сенсор успевает считать кадр. Подвох: HAL при этом **врёт в результатах** `SENSOR_FRAME_DURATION=33,3 мс`, хотя метки идут через 16,65 мс.
- **Ширик 4000×3000@60**: заполнен весь кадр.
- **Дубликатов нет**: выборочные хеши пикселей всех проанализированных кадров различны во всех режимах.

### Как это делает системная камера (C2.6, лог при записи владельцем)

- **4K60 видео**: `operation_mode 0x8021` (CamX `configure_streams() operation_mode: 32801`), ключи OCS `com.oplus.configure.video.fps=video_60fps`, H.265, `fovc=on`.
  - Файл: **HEVC Main 8 бит, BT.709 (SDR)**, 3840×2160, 60 к/с, ~68 Мбит/с.
- **HDR-видео**: при включённом HDR сессия переходит в `0x80A7` с `video_30fps`, то есть HDR у системной камеры только 30 к/с.
- **Pro RAW**: `0x8009`. DNG собирается алгоритмом **SuperRAW на DSP** (`libSuperRawPost_skel.so`, APS). Это обработанный, а не чистый RAW; размер 4096×3072.

## C3. Что вендор делает с RAW

Неподвижная сцена; ручная экспозиция 20 мс, ISO 400/3200; сравнение отношения «угол/центр» канала G и СКО центра по 4 кадрам.

| Вариант | `shading_mode` в результате | угол/центр (TL, TR, BL, BR) | СКО центра |
|---|---|---|---|
| по умолчанию | 1 | 0,288 / 0,087 / 0,458 / 0,380 | 8,25 |
| `SHADING_MODE_OFF` | **0** | 0,288 / 0,087 / 0,458 / 0,381 | 8,15 |
| + `shadingCorrection.enableShadingCorrection=0` (запрос) | 0 | то же | 8,27 |
| `sessionParameters.enableShadingCorrection=0` | 1 | то же | 8,25 |
| `sessionParameters.EnableIdealRAW=1` | 1 | то же | 8,23 |
| `sessionParameters.RawCbSourceType=1` | 1 | то же | 8,32 |
| ISO 3200: `NOISE_REDUCTION_MODE_OFF` / `HIGH_QUALITY` | 1 | то же | **45,66 / 46,32** |
| ISO 3200: `HOT_PIXEL_MODE_OFF` | 1 | то же | 45,96 |

Выводы:
1. **Коррекция виньетирования уже применена к RAW, и отключить её не удалось ни одним рычагом.** HAL честно отвечает `shading_mode=0`, но пиксели те же. Это согласуется с `SENSOR_INFO_LENS_SHADING_APPLIED=true`. Карта коррекции HAL (17×13) даёт усиление канала G в углу **×4,33** против ×1,03 в центре. На превью RAW углы не затемнены.
   - Измерить остаточную неравномерность на ровном белом поле не успели (вечер). Сделаем утром вместе с дневным набором C7.
   - Для инварианта 2 README: паспорт кадра обязан нести флаг «виньетирование скорректировано вендором» и карту коррекции. Наш ISP учитывает, что шум в углах усилен до ~4,3 раза.
2. **Шумодава в RAW нет**: СКО при NR OFF и HQ одинаково (разница 1,4% — в пределах разброса).
3. `HOT_PIXEL_MODE_OFF` разницы не дал. Выбитые пиксели отдельно не считали.
4. `dynamicBlackLevel` в результатах отсутствует. Статический black level 64 во всех каналах, `optical_black_regions` нет.
5. OIS: в характеристиках заявлен только `OFF`, но основная камера в результатах по умолчанию отвечает `ois_mode=1` (ON). Явный `OFF` принимается (результат 0). У ширика 0. Работает ли механика при OFF (дрожание против гироскопа) — **не проверено**, перенос в план `video`.

## C4. Импорт в Vulkan без копий

Команда: `pc/probe.py run oneplus vkimport camera=… format=… usages=…`. Сверка по 5 кадрам.

| Формат | usage `AImageReader` | Кадры приходят | AHB (format / stride / аллокация) | Путь импорта | GPU = CPU | GPU, мс/кадр |

- `vkGetAndroidHardwareBufferPropertiesANDROID` отдаёт `format=UNDEFINED`, `externalFormat=0`. Формат образа задаём сами (`R16_UINT`), а Adreno поддерживает его для AHB как storage-образ (`shaderStorageImageExtendedFormats`).
- Acquire-fence: HAL отдаёт уже сигнальный буфер (fd = −1). Освобождение — `AImage_deleteAsync` с release-fence, экспортированным из семафора (sync_fd). Инвариант 3 README («буфер возвращается только после GPU») реализуем штатно.
- **Инвариант 1 (0 копий) — выполним.** Блокера нет.

## C5. 50 Мп (решение 10)

**Нет, по испробованным путям.** Подробности:
- публичный RAW 8192×6144 — `configure_failed`;
- `sensor_meta_data.sensor_mode_index=0` и `org.quic.camera.QCFASnapshot=1` HAL игнорирует (режим остаётся 1);
- `com.oplus.isRawMax` / `com.oplus.ultra.high.resolution.enable` — не теги HAL;
- статика: системная камера получает полный кадр режимом `0x8001` с feature_mask `0x0010` («COMMON Single Remosaic») через сервис OCS. Pro-DNG системной камеры тоже 4096×3072.

Остаётся отдельный план: доступ к OCS или CameraUnit, либо поиск других ключей.

## Дефекты, найденные по ходу, и их причины

1. **Записи зонда пропадали из logcat.** Причина: кольцевой буфер `main` на телефоне 256 КиБ, CamX вытесняет его за секунды. Увеличивать (`logcat -G`) — менять настройку системы, это запрещено. Решение: основной канал — JSONL-файл приложения, чтение через `run-as`.
2. **Поток «зависал» после старта.** Причина: экран заблокирован (`isKeyguardShowing=true`, Doze), Activity за блокировкой, процесс фоновый, Oplus его замораживает (`isFrozen=true`). Решение: `setShowWhenLocked`/`setTurnScreenOn`, как у системной камеры.
3. **Совпадение run id у двух попыток подряд** испортило одну строку матрицы. Причина: id = время до секунды + PID. Решение: случайный суффикс, строку перепрогнали.
4. **Нативный импорт не получал кадров.** Причина: usage `GPU_DATA_BUFFER` для RAW gralloc не выделяет (см. C4). Решение: порядок usage по умолчанию начинается с `GPU_SAMPLED_IMAGE`.
5. **RAW10: сумма считалась за пределами аллокации.** Причины:
   - (а) stride AHB для RAW10 — в байтах, а считался в пикселях;
   - (б) к упакованному формату применялся путь «образ R16 4096×3072» (25 МБ поверх 15,7 МБ; драйвер такой bind не отвергает).

   Решение: трактовка stride выбирается по согласованности с `allocationSize` (тест на реальных числах телефона), упакованные форматы — только через `VkBuffer`. Проверено на телефоне: 5/5 совпадений.
6. **Блок кодеров падал целиком** на `getAchievableFrameRatesFor` для неподдерживаемого размера. Теперь это значение `unsupported_size` на кодек.
7. **Артефакт профиля полос** при высоте 3000: соседние полосы попадали в разные ряды CFA. Начало полосы теперь выровнено на чётную строку.
